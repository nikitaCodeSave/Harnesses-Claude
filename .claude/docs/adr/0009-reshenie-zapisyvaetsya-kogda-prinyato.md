# 9. Решение записывается, когда принято; `/harness:wrap` ловит пропущенное

Дата: 2026-10-30 · Решение оператора

## Context

В проекте `Statusline_Claude-Code` ADR 0010 и 0011 появились на шаге `/harness:wrap` отдельным
коммитом (`252602c`). Решения приняли в `/grill-with-docs` на полтора часа раньше. В «Охват»
`CLAUDE.md` и `.out-of-scope/` они попали коммитом без ADR (`1062a2b`), и по ним сделали ещё три
работы. Сообщение коммита с ADR: «решения, которые раньше жили только в «Охвате» CLAUDE.md».
Сжатия контекста не было, ничего не потеряно: это изъян формулировки, а не инцидент.

Причина в тексте кита. Строка шаблона про ADR говорит «written in the session where they were
made», а из команд потока ADR упоминает только `/harness:wrap` (шаг 1). Сессия, которая решает и
строит несколько задач подряд, законно копит решения до конца. `domain-modeling` из
mattpocock-skills, загруженный в грилле, ADR только предлагает, и по своему узкому порогу.

Замеренная конфигурация была другой. Плечо K многосессионного стенда L1
(`benchmark/pipeline-ab/RESULTS.md`) — основание слоя знаний в ките — работало по той же строке в
`CLAUDE.md`, но без `wrap`. По транскриптам `results-long/L1/K-*` ADR появлялись в ходе, где
собиралась фича, а решения «на будущее» — в ходе, где их назвали. В стенде сессия равна одной
фиче, поэтому «в сессии» совпадало с «вместе с изменением». В живой работе сессия длиннее, и
формулировки расходятся.

Внешние источники (`external-sources.md`, блок 4, «ADR и момент записи решения»):
- Практика ADR: где момент назван, это до решения или по ходу его — статус `proposed` (Nygard,
  Fowler), ревью до принятия (AWS), черновик ADR в PR (Red Hat), «do not defer … capturing»
  (Zimmermann). Пачкой в конце итерации не советует никто; задним числом — только для уже
  существующей системы (Azure, Spotify).
- Агентные обвязки записывают решение задачи до кода, в форме «решение / почему / отвергнутое»:
  Spec Kit `research.md`, OpenSpec `design.md`, HumanLayer «Resolved Design Questions», Superpowers
  «Approaches». Pocock: «Don't batch these up»; Spec Kit сохраняет спеку после каждого ответа «to
  minimize risk of context loss». Документация Claude Code: инструкция, данная только в разговоре,
  может не пережить сжатие.
- Против: Connell собирает ADR в конце плана, потому что агент видел всю сессию. Один практик,
  без замера.
- Ни один источник не сравнивает запись в момент решения с записью в конце сессии.

По порогу ADR источники расходятся. Узкий («архитектурно значимое», «трудно отменить»): Nygard,
AWS, Azure, GDS, ThoughtWorks, Pocock; Zimmermann называет антипаттерн «Policy in Disguise».
Широкий: MADR, Google, Spotify, Connell и наш L1, замеренный с широким порогом.

## Decision

- Строка шаблона: ADR пишется, когда решение принято, и входит в один коммит с изменением, которое
  его применяет; решение «на будущее» — когда его назвали.
- Спека из интервью несёт решения, которые оно закрыло, с причиной и отвергнутым вариантом. Строка
  стоит в *How we work* шаблона; промпт `/harness:task` не меняется — это замеренный промпт
  интервью.
- Шаг 1 `/harness:wrap` — проверка: дописывает ADR для решений, не записанных вовремя, и называет
  их. Шаг 4 — перенос строк спеки при закрытии — остаётся: закрытие и есть его момент (так же
  устроен архив OpenSpec).
- Порог ADR не меняется. Сужение отложено: источники расходятся, по рубрике блока 10 такое решает
  собственный стенд, а единственный замер сделан с широким порогом.

## Consequences

- Кит: шаблон `CLAUDE.md`, `wrap`, руководства, README (основание строки), CHANGELOG; M9 проверяет
  новые фразы шаблона и `wrap`.
- Лаборатория: `workflow.md` говорит то же. Правило для собственных ADR лаборатории (`AGENTS.md`)
  этим решением не меняется.
- В проектах, где шаблон уже поставлен (`Statusline_Claude-Code`), строка меняется отдельно.
- Не измерено, влияет ли момент записи на сохранность решений. Основание — сходящаяся практика и
  механика сжатия, а не эксперимент.
