# Documentation discipline (harness invariant)

7 правил поддержки проектной документации, инвариантных для любого стека. Расширяется проектным CLAUDE.md, не заменяется. Rule #0 — рамка для остальных: он решает, писать ли документ вообще.

Continuity здесь нет: состояние между сессиями держит открытая спека (или трекер), решения — ADR (rule 6); носитель журнала не заводится там, где его ещё нет. Дублировать это отдельным файлом в проекте нельзя.

Bootstrap canonical layout (`docs/ARCHITECTURE.md` / `CODE-MAP.md` / `GLOSSARY.md` / `CONVENTIONS.md` / `ADR/` / `RUNBOOKS/`) — нативно под способной моделью (read-before-write, реальное содержимое не boilerplate; рычаг — `WORKFLOW.md` §3). Этот rule — ongoing discipline поверх bootstrap'а.

0. **Оракул раньше прозы. Документируется только невыводимое.** Прежде чем писать или обновлять документ — проверь, закрывается ли утверждение **исполняемым оракулом**: тестом, типом, схемой, линтером, деструктурирующей проверкой. Если да — оракул и есть документация, проза не пишется. Документ несёт то, чего в коде нет и быть не может: ратифицированное решение с датой и автором, **измеренную** причину выбора (с цифрой), намеренное удержание кода без вызывающего, явный non-claim. Проза, пересказывающая схему, таблицу модулей, список guard'ов или импорт-граф, **удаляется, а не актуализируется**: у неё нет оракула, поэтому она расходится с кодом молча, и «частично верный документ опаснее отсутствующего».

   Порядок закрепления инварианта: тест → тип/схема → правило-с-проверкой → проза. Проза — последнее средство, а не первое.

   **Критерий применяется к отдельному утверждению, а не к файлу.** Документ-дубль почти всегда содержит несколько строк, которых нет нигде больше — чаще всего это запрет *действия* («не выводить код из текста», «не вызывать producer ради счётчика», «смена смысла поля требует новой версии»). Тип и тест выражают допустимые значения, но не запрещённые действия, поэтому такие строки невыводимы по природе. Удаление файла целиком их теряет молча (одна независимая проверка такой правки нашла 4 потерянных утверждения в 4 удалённых доках — [запись](../devlog/entries/0137-dokumentatsiyu-dushil-ne-dreyf-a-stoimost-ee-podderzhki.md)). Перед удалением — построчный проход с вопросом «где ещё это сказано», и отдельная проверка свежим контекстом для правок этого класса.

   Признак нарушения, который видно из репозитория: доля коммитов, трогающих только `.md`, устойчиво выше доли коммитов в код. Это не «хорошая дисциплина», это налог — документация растёт быстрее, чем система, которую она описывает (замер на живом проекте: 55% коммитов только-`.md`, 63k строк прозы на 100k строк кода при 35k строк тестов, причём ни один док не был устаревшим — цена платилась постоянным ремонтом; [запись](../devlog/entries/0137-dokumentatsiyu-dushil-ne-dreyf-a-stoimost-ee-podderzhki.md)).

1. **Doc-with-code rule** (в пределах rule #0). PR, меняющий архитектуру / добавляющий top-level dir / вводящий domain-термин / устанавливающий новую convention — обязан в **том же** PR обновить оракул, а документ — только если утверждение оракулом не закрывается. Reviewer (включая Claude) отклоняет PR, где граница модулей описана абзацем вместо теста.

   **Mapping diff → документ** (классифицируй каждый изменённый файл по характеру правки; один файл может попасть в несколько строк). Под способной моделью это нативная работа main thread'а из git diff — **отдельный skill не нужен** (его ядро — эта таблица):

   | Категория изменения | Признак в diff | Куда (оракул раньше прозы) |
   |---|---|---|
   | Структурное | новый/удалённый/переименованный модуль, top-level каталог, точка входа | тест границ (`test_architecture_boundaries`-класс) — он и есть карта; в прозу только то, что тест не выражает |
   | Поток данных / зависимости | изменён import-граф, новый шаг пайплайна, новый внешний сервис | тот же тест границ; `ARCHITECTURE.md` — лишь если решение требует «почему» |
   | Новый domain-термин | впервые встречается имя сущности / аббревиатура | `GLOSSARY.md` (см. rule #5) |
   | Новая convention | новый паттерн именования, layout, протокол, стиль | `CONVENTIONS.md` |
   | Конфигурация / setup | новый env-var, параметр конфига, шаг установки, зависимость | `README.md` (+ setup-doc если есть) |
   | Операционная процедура | новый деплой / миграция / recovery-сценарий | `RUNBOOKS/` |
   | Архитектурное решение | выбор lib A vs B, протокол, осознанный отказ от refactor'а | `ADR/` (порог — rule #6) |

   Правь **только затронутые разделы**, не весь документ. Эскалация (не «чинить» молча): расхождение 3+ модулей с `ARCHITECTURE.md` — это уже re-bootstrap (перечитать код, переписать canonical docs целиком, read-before-write), а не точечный sync; противоречие между `ARCHITECTURE.md` и `CLAUDE.md`; `CLAUDE.md` дублирует содержимое `docs/` (нарушение rule #2).

2. **CLAUDE.md как indexer, не store**. CLAUDE.md ссылается на `docs/ARCHITECTURE.md` / `docs/CODE-MAP.md` / `docs/GLOSSARY.md` / etc., но не дублирует их содержимое. Цель: проектный CLAUDE.md ≤ 200 строк. Длиннее — split в `docs/` или paths-scoped rules.

3. **Инструкции описывают настоящее; история — в записях.** Инструкции (`CLAUDE.md`, `AGENTS.md`, rules, skills, рабочие доки) говорят, как есть и почему: правило и его причину, с цифрой, если она несёт решение. В них нет дат, номеров версий, ссылок на журнал и рассказа «как было» — всё это устаревает и занимает контекст. История живёт в записях: git и сообщения коммитов, ADR (принятый не правится — его отменяет следующий), `RESULTS.md` стендов, CHANGELOG, один версионный справочник (в лабе — `native-capabilities.md`). Архивы (`.claude/docs/archive/`, `.claude/devlog/`) и записанные аудиты (`.claude/audits/<slug>/`) заморожены; новый аудит пишет свою папку. Инструкция ссылается на запись, а не пересказывает её; удалённый компонент из инструкций просто исчезает.

   **Sentence-level (внутри live reference/product-дока — `ARCHITECTURE`/`PRD`/`CODE-MAP`/`GLOSSARY`/`README`):** такой док — снимок «как есть сейчас», не журнал изменений. Нарратив перехода (`было→стало`, «ранее»/«теперь» как пометка о правке, «замещает прежнее решение», `X→Y`, «⚠ ИЗМЕНЕНО») принадлежит git-диффу и сообщению коммита, не телу дока. Обоснование текущего выбора («почему так») сохраняй; *что* было раньше и что это reversal — в ADR-supersedes / коммит. При правке вычищай осевшие рядом следы прошлых правок. **Карваут:** ADR и CHANGELOG — записи, датированный провенанс в них намеренный. Замер (не перемерен на текущем поколении моделей): без правила переходный нарратив утекал в док в 3 из 3 случаев на reversal-решениях и многосессионном накоплении, с правилом — 0 из 3 без потери фактов; чистая замена факта утечки не даёт и без правила (0 из 4) — [запись](../devlog/entries/0113-empiricheskiy-analiz-stale-transition-markers-sentence-level.md).

4. **Владелец и свежесть.** У каждого дока в `docs/` есть владелец (`owner: @<handle>` во frontmatter или CODEOWNERS). Свежесть берётся из git (`git log -1 --format=%cs -- <doc>`), а не из поля даты, которое забывают обновить. Не менялся больше 6 месяцев — кандидат на review.

5. **Glossary first-use**. Первое использование акронима / domain-термина в любом doc, коммите или комментарии → запись в `docs/GLOSSARY.md`.

6. **ADR для non-trivial решений**. Любое решение, которое будущему контрибьютору было бы непонятно «почему так» (выбор lib A vs B, layout, protocol, отказ от refactor'а) → 1-page ADR в формате Context / Decision / Consequences / Alternatives considered. Threshold: если объяснение решения в Slack заняло >5 минут — ADR.

См. также `.claude/docs/principles.md` и `.claude/docs/memory-layers.md`.
