# pipeline-ab — результаты

Дизайн, гипотезы и правила решения — `README.md` (записаны до соответствующих прогонов). Модель
`claude-opus-5-5`, effort `high`, симулятор `claude-sonnet-5-5`. Данные — `results/` (основная
матрица) и `results-busy/` (добивающий тест), `<task>/<arm>-<rep>/score.json`.

## Валидность

63 прогона. Три признаны недействительными по вине обвязки и перезапущены; оригиналы лежат в
`invalid/` как провенанс:

- **busy T1 R-3** — симулятор ответил на вопросы, но пометил ход `done`; агент ответов не получил,
  `SPEC.md` не был написан; стадия Check нашла `find /`-ом и прочитала `SPEC.md` чужого прогона
  основной матрицы (сам симулятор тоже прочитал его и разрешил использовать) — **заражение**.
- **busy T1 F-1** — ответ симулятора без строки JSON засчитан как `done`, спека не написана.
- **основная T3 R-3** — тот же сбой разбора; требования агент добрал у симулятора на стадии Check, в
  обход порядка стадий (заражения нет).

Исправления перед перезапуском: `permissions.blockReadsOutsideWorkingDirectories` для всех сессий,
включая симулятор (проверено: блокирует `find`, `cat` и Read вне рабочего каталога); содержательный
ответ симулятора доходит до агента даже с меткой `done`; оператор проверяет `SPEC.md` после стадии
Spec. Скан транскриптов всех 63 прогонов: обращения к чужим рабочим каталогам были только у двух
недействительных; перезапуски чисты. В оставшихся прогонах 29 ходов симулятора с текстом и меткой
`done` — все подтверждения уже сделанной работы («спека совпадает», «не возражаю»); у всех этих
прогонов спека на месте.

## Решения

1. **Поток по умолчанию для работы, помещающейся в одну сессию — S:** интервью → `SPEC.md`
   (интерфейс из запроса дословно, ограничения scope) → сборка в той же сессии → «готово» с
   командой и выводом.
2. **Эскалации, а не дефолт:** работа на несколько сессий → приёмочные тесты из спеки отдельным
   контекстом до свежей сборки (без них F терял требования, с ними R держал 18/18); high-stakes и
   silent-wrong → одно ревью свежим контекстом против спеки, ≤3 раундов.
3. **Не по умолчанию для работы в одну сессию:** ваниль без интервью (3/9 при реалистичном пользователе); полный пайплайн
   Pocock (в 3.1–4.4 раза дороже R, который сам в 2.2–4.9 раза дороже S; 12–22 субагента без прироста).
4. **TDD снят** — подтверждено H2 (с оговоркой о составе набора R; чистое сравнение S и V с P — там же).
5. Расхождение с first-party: best-practices советует строить по `SPEC.md` в свежей сессии; на
   задачах этого размера свежая сессия без независимых тестов хуже той же сессии.

**Граница вывода (уточнено оператором 2026-10-28).** Стенд мерил задачи в одну сессию на свежем репо —
там слою знаний Pocock (глоссарий, ADR, спеки и тикеты в трекере, `wayfinder`, `retro`) окупиться негде.
Ценность слоя для долгих проектов измерил многосессионный стенд — раздел ниже.

## Ограничения

Три небольшие задачи на Python stdlib, одна модель, симулятор вместо человека; потолок приёмки на
T1/T2 оставляет различиям мало места. Плечо R спроектировано экспериментатором, а его промпт Spec
поправлен после дыма на T3 (раскрыто в README). Сравнение P с S — через R, напрямую в одном режиме
пользователя они не прогонялись. Не измерено: работа больше одной сессии, на которой эскалация
«Check до свежей сборки» и обоснована.

лёгкие правила знаний (термины в `GLOSSARY.md`, решения — включая названные «на будущее» — в `docs/adr/` в той
же сессии, читать их перед работой); на передовой модели это страховка ценой ~+17%, на слабой — разница
между потерей и переносом знаний. Инструменты Pocock — там, где этот стенд их не мерил: работа больше одной
сессии (`/to-spec` → `/to-tickets` и трекер как состояние работы, тикетам — исполнимые критерии),
большая работа в тумане (`/wayfinder`), `/retro` после вехи. Полный пайплайн Pocock на каждую фичу — не по
умолчанию.

**Ограничения:** один проект, три фичи, пять решений «на будущее», одна модель; месяцы накопления (десятки фич
и решений, разрастание одного `SPEC.md`) не моделировались — именно там структура ADR вероятнее окупается, но
это не измерено.
