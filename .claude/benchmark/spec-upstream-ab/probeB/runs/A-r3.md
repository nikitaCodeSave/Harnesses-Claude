# Ревью диффа `app/bank_import.py`

**Итог:** три [hard]-ограничения из SPEC (R3, R4) нарушены, плюс SQL-инъекция на пути необработанных данных из банка. Дифф не готов к мержу.

---

## CRITICAL

### 1. SQL-инъекция: номер счёта подставляется в запрос через f-string
`app/bank_import.py:67-69`

```python
account = conn.execute(
    f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
).fetchone()
```

Единственное место в коде, где не используется параметризация — и именно там, где значение приходит из внешнего CSV. Проверено:

- `account = "ACC-1' OR '1'='1"` → строка **разнесена**, 999 ушло на ACC-1, хотя такого счёта в выгрузке нет. Деньги можно направить на произвольный счёт, подсунув файл.
- Легитимные данные тоже ломаются: счёт `O'BRIEN-1` → `OperationalError: near "BRIEN": syntax error`.

Ниже в этой же функции все остальные запросы параметризованы — то есть это не стиль, а пропуск.

### 2. R3 нарушен: `commit()` внутри цикла — файл разносится частями
`app/bank_import.py:50-54`

```python
for idx, row in enumerate(rows, start=1):
    _apply_row(conn, row)
    conn.commit()          # ← коммит на каждую строку
```

R3 `[hard]`: «Импорт файла атомарен: применён целиком либо не применён вовсе». Acceptance criterion 4 — то же самое. Проверено на файле из 3 строк, где 2-я падает (`unknown account`):

```
упало: ValueError unknown account for payment P-2
остатки после сбоя: {'ACC-1': 100, 'ACC-2': 0}   # ожидалось {'ACC-1': 0, 'ACC-2': 0}
```

Ровно то полу-разнесённое состояние, которое SPEC объявляет недопустимым. Нужен один транзакционный блок на весь файл (`with conn:` / явный `BEGIN`…`COMMIT`), коммит после цикла.

### 3. R4 нарушен: телефон клиента пишется в лог
`app/bank_import.py:59-64`

```python
log.info("payment %s account=%s phone=%s", row["payment_id"], row["account"], row["phone"])
```

R4 `[hard]`: «Персональные данные из выгрузки (телефон клиента) не попадают в логи». Проверено — в лог-хендлер уходит:

```
payment P-1 account=ACC-1 phone=+79990000001
```

Уровень INFO, то есть в проде это попадёт в файлы/агрегатор. Поле `phone` в разноске вообще не используется — его достаточно просто не читать.

## MAJOR

### 4. Коррекция со сменой счёта портит остатки **обоих** счетов
`app/bank_import.py:67-72` + `89-109`

`existing` ищется только по `payment_id`, без учёта счёта, а откат старой суммы применяется к балансу **нового** счёта. Проверено: P-1 = 100 на ACC-1, затем повтор P-1 = 130 на ACC-2:

```
после коррекции: {'ACC-1': 100, 'ACC-2': 30}   # ожидалось {'ACC-1': 0, 'ACC-2': 130}
```

На ACC-1 проводка аннулирована, но деньги не сняты; ACC-2 получил `130 - 100 = 30`. Двойная ошибка в деньгах, молча, без исключения. Откат старой суммы должен идти на `account_id` **старой** проводки (которого запрос сейчас даже не выбирает — `SELECT amount` вместо `SELECT amount, account_id`).

### 5. Смена счёта при неизменной сумме игнорируется полностью
`app/bank_import.py:89-91`

```python
if old_amount == amount:
    return
```

Ранний выход сравнивает только сумму. Если банк прислал тот же платёж с исправленным счётом — ничего не произойдёт: ни аннулирования, ни аудит-записи, ни переноса денег. Проводка навсегда останется на неверном счёте, и повторный импорт это не вылечит. Та же корневая причина, что и в п. 4: идентичность проводки сведена к `(payment_id, amount)`.

### 6. Остаток пишется абсолютным значением по прочитанному ранее балансу
`app/bank_import.py:84-86`, `106-109`

```python
account_id, balance = account            # читаем
...
conn.execute("UPDATE accounts SET balance = ? WHERE id = ?", (balance + amount, account_id))
```

Классический lost update: между SELECT и UPDATE любое другое изменение баланса затирается. В связке с покомандным коммитом (п. 2) окно между чтением и записью реально открыто для другой сессии. Правильно — относительный апдейт: `SET balance = balance + ?`; заодно исчезает необходимость тащить `balance` из первого запроса.

### 7. Схема не запрещает несколько активных проводок по одному `payment_id`
`app/bank_import.py:16-21`

У `postings` нет ни PK, ни уникального индекса. При этом код читает активную проводку через `.fetchone()` — то есть при двух активных строках молча берёт одну, — а аннулирует через `UPDATE ... WHERE state='active'` **все**. Баланс при этом корректируется только на один `old_amount` → расхождение остатка без единой ошибки в логе. Инвариант «не более одной активной проводки на платёж» — это то, на чём держится вся идемпотентность (R1), и он не выражен в схеме. Нужен `UNIQUE`-индекс (частичный: `WHERE state = 'active'`) и/или `CHECK (state IN ('active','annulled'))`.

## MINOR

### 8. `file_digest` вычисляется, но не используется
`app/bank_import.py:36-38`, `43-44` — хеш считается, логируются первые 12 символов, дальше значение нигде не участвует. Похоже на недоделанную дедупликацию по файлу — то есть ровно на тот механизм, которого требовала исходная проблема из SPEC («банк дважды прислал одну и ту же выгрузку»). Сейчас это создаёт ложное впечатление, что защита на уровне файла есть. Либо довести до реальной проверки, либо убрать. Побочно: `fh.read()` тянет файл целиком в память, и следом `list(csv.DictReader(...))` — второй раз.

### 9. Аудит-след не связывает аннулированную проводку с заменившей
`app/bank_import.py:22-27`, `97-105` — R2 `[hard]` («что было, что стало, когда») формально выполнен, но acceptance criterion 3 говорит «по **любой** аннулированной проводке увидеть, на что её заменили». У `postings` нет ни `id`, ни `created_at`, аудит ссылается только на `payment_id` + суммы. На последовательности 100 → 130 → 100 сопоставить конкретную аннулированную строку с её аудит-записью уже нельзя однозначно.

### 10. Открытый вопрос SPEC решён молча — и решён наполовину
`app/bank_import.py:70-71` — SPEC, раздел «Открытое»: строки с неизвестным счётом «отбрасывать с отчётом или блокировать весь файл — решение не принято». Код выбрал «блокировать», не пометив это как решение. Хуже того, из-за п. 2 он блокирует *после* частичной разноски — то есть не реализует ни один из двух вариантов. Это решение стоит вынести пользователю явно.

### 11. Нет валидации строки выгрузки
`app/bank_import.py:65` — `int(row["amount"])` на `"100.50"` даёт `ValueError: invalid literal for int() with base 10: '100.50'` без указания номера строки и `payment_id`. Отсутствующая колонка в CSV → голый `KeyError`. Отрицательные суммы, пустой `payment_id` не проверяются. Для файла, приходящего извне и обрабатываемого бухгалтером вручную, сообщение об ошибке должно называть строку.

### 12. Возвращаемое значение не соответствует докстроке
`app/bank_import.py:42`, `49-55` — «Возвращает число применённых строк», но счётчик инкрементируется на каждой итерации, включая no-op. Проверено: повторный импорт того же файла ничего не меняет и возвращает `2`. Бухгалтер по этому числу увидит «применено 2» там, где применено 0.

### 13. `print()` в бизнес-логике
`app/bank_import.py:54` — R5 `[soft]` про прогресс в консоли выполнен, но I/O вшит в функцию разноски: её нельзя вызвать из другого контекста без мусора в stdout, и в модуле теперь сосуществуют два канала вывода (`logging` и `print`). Прогресс лучше вынести в вызывающий CLI (callback/`log`).

### 14. Производительность
`app/bank_import.py:74-77` — по `postings.payment_id` нет индекса, поиск активной проводки — full scan на каждую строку файла; при растущей таблице импорт деградирует квадратично. Плюс `commit()` на строку = fsync на строку.

### 15. Мусор в рабочем дереве
Незакоммиченные пустые `err.log` и `out.md` в корне. Отдельно (не из этого диффа, но всплывает рядом): в git **отслеживаются** `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` — они «изменяются» при каждом прогоне тестов. Нужен `.gitignore`.

## Пробел в тестах

`tests/test_bank_import.py` покрывает критерии 1–3 в happy-path. Не покрыто ни одного из нарушенных [hard]-ограничений: нет теста на атомарность (R3), на отсутствие PII в логах (R4), на инъекцию/спецсимволы в номере счёта, на смену счёта у существующего платежа. Тесты зелёные — и при этом все три критические находки живы. Для класса «тихо неверно» (деньги) эти сценарии стоит зафиксировать тестами до правок.

## Приоритет починки

1. Параметризовать запрос по `number` (п. 1) — одна строка, снимает и инъекцию, и падение на апострофе.
2. Один коммит на файл + `with conn:` (п. 2) — снимает R3 и заодно частичную разноску при неизвестном счёте.
3. Убрать `phone` из лога (п. 3) — одна строка, R4.
4. Учитывать счёт в идентичности проводки и делать относительный апдейт баланса (пп. 4–6) — это переписывание `_apply_row`, здесь и стоит начать с падающих тестов.
5. `UNIQUE`-индекс на активную проводку (п. 7) — фиксирует инвариант в схеме, а не в коде.
