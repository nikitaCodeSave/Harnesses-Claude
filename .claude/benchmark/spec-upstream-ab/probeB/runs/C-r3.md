# Ревью диффа: `app/bank_import.py`

Дифф превращает скелет (`raise NotImplementedError`) в рабочий импортёр банковской выгрузки. Логика идемпотентности и коррекций в целом задумана верно, но содержит два дефекта, при которых деньги молча оказываются на неверном счёте, и один класс дефектов вокруг транзакционности.

Все три существующих теста зелёные — и ни один из найденных сценариев не покрывают.

---

## CRITICAL

### 1. SQL-инъекция в поиске счёта — `app/bank_import.py:67-69`

```python
account = conn.execute(
    f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
).fetchone()
```

Единственный запрос в файле, собранный f-строкой; все остальные (строки 75, 81, 85, 94, 98, 102, 107) используют биндинг параметров. Данные приходят из внешнего CSV банка.

Подтверждено запуском:

- `account = "NOPE' OR '1'='1"` → предикат вырождается, `fetchone()` возвращает **первый попавшийся счёт**, 999 зачислено на `ACC-1`. Проверка `if account is None` не срабатывает, ошибки нет, в журнале — валидная проводка.
- Легитимный номер счёта с апострофом (`O'BRIEN-1`) роняет импорт: `OperationalError: near "BRIEN": syntax error`.

То есть это одновременно дыра в безопасности и баг корректности на честных данных. Многооператорную инъекцию (`; DROP TABLE`) sqlite3 `execute` не пропустит, но зачисление на произвольный счёт и так достаточно.

**Суть:** параметризовать запрос — `WHERE number = ?`.

---

### 2. Коррекция со сменой счёта разносит деньги неверно — `app/bank_import.py:74-109`

Существующая проводка ищется **только по `payment_id`** (строка 75), а `account_id`/`balance` берутся из **текущей** строки CSV (строки 67-72). Ветка коррекции молча предполагает, что счёт не менялся.

Подтверждено запуском:

| Сценарий | Факт | Ожидание |
|---|---|---|
| `P-1: ACC-1 100` → коррекция `P-1: ACC-2 130` | `ACC-1=100, ACC-2=30` | `ACC-1=0, ACC-2=130` |
| `P-1: ACC-1 100` → коррекция `P-1: ACC-2 100` | `ACC-1=100, ACC-2=0` (полный no-op) | `ACC-1=0, ACC-2=100` |

Механика первого случая: `balance - old_amount + amount` на строке 108 вычитает `old_amount` из баланса **нового** счёта (`0 - 100 + 130 = 30`), а старый счёт никто не сторнирует. Второй случай ещё хуже — ранний выход `if old_amount == amount: return` (строки 90-91) сравнивает только сумму, поэтому коррекция, меняющая **только** счёт, отбрасывается целиком и бесследно.

Оба случая проходят без единой ошибки или предупреждения — классический silent-wrong: не тот клиент списан/зачислен.

**Суть:** ключ дедупликации — `payment_id`, но эффект проводки зависит от пары (`account_id`, `amount`). Сторнирование должно откатывать `old_amount` с **исходного** счёта проводки (его надо читать из `postings`, а не из CSV), и лишь затем начислять на новый.

## MAJOR

### 3. Commit на каждой строке → частичный импорт файла — `app/bank_import.py:50-53`

```python
for idx, row in enumerate(rows, start=1):
    _apply_row(conn, row)
    conn.commit()
```

Файл — не атомарная единица. Исключение на строке N (например, `ValueError` неизвестного счёта со строки 71) оставляет строки 1..N-1 зафиксированными в БД, а `import_file` не возвращает ничего и не оставляет маркера прогресса.

Подтверждено: файл `[P-1 ok, P-2 неизвестный счёт, P-3 ok]` → `ValueError`, но `ACC-1=100` и проводка `P-1` уже в базе; `P-3` не применена.

Повторный прогон здесь спасает только благодаря построчной идемпотентности — то есть корректность после сбоя держится на побочном свойстве, а не на транзакции. Плюс `commit()` на строку — это fsync на строку, дорого на дневной выгрузке.

**Суть:** один commit на файл (или явный `with conn:`), rollback при ошибке.

### 4. Телефон клиента (PII) в логах уровня INFO — `app/bank_import.py:59-64`

```python
log.info("payment %s account=%s phone=%s", row["payment_id"], row["account"], row["phone"])
```

Номер телефона + номер счёта + идентификатор платежа пишутся в лог на каждую строку выгрузки, на INFO, то есть в обычном проде. Логи обычно уходят в агрегатор с более длинным сроком хранения и более широким доступом, чем сама биллинговая БД. Для биллинга это прямой вопрос к 152-ФЗ/GDPR.

Поле `phone` в остальном коде **вообще не используется** — оно читается исключительно ради этой строки лога (и попутно создаёт жёсткую зависимость от колонки, см. п. 6).

**Суть:** убрать `phone` из лога; при необходимости — маскировать и понизить до DEBUG.

### 5. Read-modify-write баланса в Python вместо атомарного UPDATE — `app/bank_import.py:84-86, 106-109`

```python
conn.execute("UPDATE accounts SET balance = ? WHERE id = ?", (balance + amount, account_id))
```

`balance` прочитан на строке 72 отдельным `SELECT`, новое значение считается в Python и записывается как константа. В legacy-режиме `sqlite3` `SELECT` не открывает транзакцию, поэтому два параллельных импорта (или импорт + любой другой процесс, меняющий баланс) прочитают одно и то же значение, и последний commit затрёт первый — платёж исчезает бесследно.

Для дневной выгрузки конкуренция, возможно, сегодня не возникает, но защиты от неё нет никакой, а цена ошибки — потерянные деньги.

**Суть:** `SET balance = balance + ?` — арифметика на стороне БД, тогда гонка исключена конструктивно.

### 6. Нет валидации входного CSV — `app/bank_import.py:58-72`

Все поля читаются в предположении идеального файла. Подтверждено запуском:

- `int(row["amount"])` (строка 65) падает `ValueError` на `""`, `"100.50"`, `"1 000"` — типовые варианты банковской выгрузки. В сочетании с п. 3 это обрывает импорт на середине.
- Отсутствие колонки `phone` в заголовке → `KeyError: 'phone'`, без указания файла/строки. Заголовок нигде не проверяется.
- **Отрицательная сумма принимается молча**: `-500` → `ACC-1 = -500`. Ни знак, ни ноль, ни разумный потолок не проверяются.

**Суть:** валидировать заголовок один раз перед циклом, оборачивать разбор строки с указанием номера строки, явно решить вопрос со знаком суммы.

### 7. Схема без ограничений и индексов — `app/bank_import.py:16-27`

```sql
CREATE TABLE IF NOT EXISTS postings (
    payment_id TEXT NOT NULL, account_id INTEGER NOT NULL,
    amount INTEGER NOT NULL, state TEXT NOT NULL DEFAULT 'active'
);
```

- **Нет индекса на `payment_id`.** `EXPLAIN QUERY PLAN` подтверждает `SCAN postings` для запроса на строке 74-77 — полный проход таблицы на каждую строку выгрузки, то есть O(n²) по мере роста таблицы проводок.
- **Инвариант «одна активная проводка на `payment_id`» ничем не защищён.** Код на него опирается: строка 77 берёт `fetchone()` (одну), а строка 93-96 аннулирует `WHERE payment_id = ? AND state = 'active'` (все). Если по любой причине активных окажется две, все они аннулируются, а баланс скорректируется лишь на один `old_amount` — тихое расхождение. Нужен частичный уникальный индекс: `CREATE UNIQUE INDEX ... ON postings(payment_id) WHERE state = 'active'`.
- Нет `FOREIGN KEY (account_id) REFERENCES accounts(id)`, нет `CHECK (state IN ('active','annulled'))`, у `postings` нет первичного ключа.

## MINOR

### 8. `file_digest` вычисляется и не используется — `app/bank_import.py:36-44`

Хеш считается по всему файлу, логируются первые 12 символов — и всё. Нигде не сохраняется и не сверяется. Наличие функции с таким именем создаёт впечатление защиты от повторного импорта файла, которой нет (защита на самом деле построчная). Плюс `fh.read()` тянет весь файл в память ради одного лог-сообщения.

Либо использовать по назначению (таблица обработанных файлов), либо убрать.

### 9. `print()` в библиотечной функции — `app/bank_import.py:54`

`print(f"  [{idx}/{len(rows)}] {row['payment_id']}")` в модуле, который в остальном пользуется `logging`. Пишет в stdout, не отключается, не форматируется, мешает вызову из другого кода и засоряет вывод тестов.

### 10. Файл целиком в памяти — `app/bank_import.py:47`

`rows = list(csv.DictReader(fh))` — нужен только для `len(rows)` в `print` из п. 9. Убрав `print`, можно итерировать потоково.

### 11. `changed_at` без указания таймзоны — `app/bank_import.py:103`

`datetime('now')` в SQLite отдаёт UTC, но в аудит-таблице это записано как строка без маркера зоны. При разборе инцидента это стабильный источник путаницы. Стоит писать ISO-8601 с суффиксом `Z`.

### 12. Мусор в рабочем каталоге

`err.log` и `out.md` — пустые неотслеживаемые файлы. Отдельно (это pre-existing, не из диффа): в репозиторий закоммичены `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` — нужен `.gitignore`.
