## Ревью рабочего диффа

Дифф: `app/bank_import.py` (+98/−3) — реализация импорта банковской выгрузки поверх скелета. Тесты (`3 passed`) зелёные, но покрывают только «счастливый» сценарий: один и тот же счёт, корректный CSV, один поток. Все находки ниже воспроизведены исполнением реального кода.

---

### CRITICAL

**1. SQL-инъекция: номер счёта из CSV подставляется в запрос f-строкой**
`app/bank_import.py:67-69`

```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```

Единственный непараметризованный запрос во всём файле — остальные корректно используют `?`. Данные приходят из внешнего файла выгрузки, то есть источник недоверенный. Воспроизведено:

| Значение `account` в CSV | Результат |
|---|---|
| `' OR 1=1 --` | импорт проходит без ошибки, 999 зачислено на **чужой** счёт `ACC-1` (счёта с таким номером не существует) |
| `ACC-9' UNION SELECT id, 999999 FROM accounts WHERE number='ACC-1` | проводка на 1, а баланс `ACC-1` выставлен в **1 000 000** — подделан `balance`, который затем пишется через `UPDATE` |
| `O'BRIEN-1` (легитимный номер с апострофом) | `OperationalError: near "BRIEN": syntax error` — падение на валидных данных |

Третья строка показывает, что это не только атака: обычный апостроф в номере счёта роняет импорт.

**2. Коррекция со сменой счёта разносит деньги неверно на обоих счетах**
`app/bank_import.py:106-109` (в связке с `72`)

`balance` читается для счёта **из новой строки**, а `old_amount` — из старой проводки, которая могла быть на **другом** счёте. Формула `balance - old_amount + amount` молча предполагает, что счёт не менялся. Сценарий: платёж `P-5` пришёл на `ACC-1` (100), затем исправлен на `ACC-2` (130):

```
ACC-1  balance=100  sum(active)=0    <<< MISMATCH  (проводка аннулирована, деньги не сняты)
ACC-2  balance=30   sum(active)=130  <<< MISMATCH  (0 - 100 + 130 вместо +130)
```

Инвариант «баланс = сумма активных проводок» ломается сразу на двух счетах: на старом зависают лишние 100, новый недополучает 100. Тесты этот кейс не проверяют — в них счёт при коррекции всегда тот же.

**3. Импорт файла неатомарен: `commit` на каждой строке, откатить частичный импорт нечем**
`app/bank_import.py:50-53`, `71`

`conn.commit()` внутри цикла фиксирует каждую строку по отдельности, а `_apply_row` бросает `ValueError` на неизвестном счёте. Файл из 3 строк с битой второй:

```
raised: ValueError - unknown account for payment P-2
balances after crash: ACC-1: 100, ACC-2: 0
postings: [('P-1', 100, 'active')]
```

`P-1` закоммичен, `P-3` не разнесён, вызывающий получает исключение и не знает, что именно применилось. Для денежных проводок дневная выгрузка должна применяться целиком либо не применяться вовсе.

### MAJOR

**4. Read-modify-write баланса вместо атомарного инкремента + нет уникального ограничения на активную проводку**
`app/bank_import.py:72`, `84-86`, `106-109`; схема — `16-21`

Баланс вычисляется в Python (`balance + amount`) из ранее прочитанного значения. Классический lost update. Плюс дедупликация по `payment_id` держится только на проверке в коде (`74-77`) — в схеме нет ни `PRIMARY KEY`, ни `UNIQUE`. Два параллельных импорта одного файла: оба читают `balance=0` и `existing=None`, оба вставляют проводку —

```
balance: 100  (одно из двух обновлений потеряно)
active postings for P-C: 2  -> дубль ничем не остановлен
```

Лечится связкой `SET balance = balance + ?` и частичного уникального индекса по `payment_id` при `state='active'`. Отдельно: `fetchone()` на строке 77 при уже возникшем дубле молча возьмёт произвольную из двух активных проводок.

**5. PII в логах: телефон клиента пишется на каждую строку**
`app/bank_import.py:59-64`

`log.info("payment %s account=%s phone=%s", ...)` — номер телефона и номер счёта уходят в лог-агрегатор на уровне INFO. Это персданные (152-ФЗ/GDPR), для работы функции телефон вообще не нужен — он нигде дальше не используется. Строка `54` дополнительно печатает `payment_id` в stdout.

**6. `import_file` коммитит соединение, которым владеет вызывающий**
`app/bank_import.py:52` (и `init_db:32-33`)

Функция принимает готовый `Connection`, но безусловно коммитит его — вместе с любой незакоммиченной работой вызывающего. Воспроизведено: вызывающий вставляет строку, вызывает `import_file`, затем делает `rollback()` — строка всё равно остаётся в БД (`TEMP-9 = 777`). Импорт нельзя встроить в более крупную транзакцию. `executescript` в `init_db` тоже делает неявный commit.

**7. `file_digest` вычисляется, логируется и не используется**
`app/bank_import.py:36-38`, `43-44`

Хеш файла создаёт впечатление защиты от повторного импорта, но нигде не сохраняется и не сверяется — идемпотентность фактически обеспечивается только проверкой по `payment_id`. Либо мёртвый код, либо недоделанная фича; в текущем виде вводит в заблуждение при чтении. Побочно: `fh.read()` тянет файл целиком в память.

### MINOR

**8. Возвращаемое значение `applied` не соответствует докстрингу**
`app/bank_import.py:42`, `49-55` — считаются все строки файла, включая no-op-ветку `90-91`. Повторный импорт того же файла возвращает `1` при нуле реально применённых строк. Значение непригодно для отчётности/мониторинга.

**9. CSV с BOM роняет импорт**
`app/bank_import.py:46` — `encoding="utf-8"` вместо `utf-8-sig`. Банковские выгрузки из Windows-систем регулярно приходят с BOM; первый ключ становится `\ufeffpayment_id`:
```
raised: KeyError - KeyError('payment_id')
```

**10. Нет валидации входных полей**
`app/bank_import.py:65` — `int(row["amount"])` на дробной сумме даёт `ValueError: invalid literal for int() with base 10: '100.50'` без указания строки/платежа; отрицательные суммы не проверяются; отсутствие колонки в CSV даёт голый `KeyError`. Ни одна ошибка не привязана к номеру строки файла.

**11. `print()` в библиотечном коде**
`app/bank_import.py:54` — прогресс-вывод в stdout при уже настроенном `logging`. Не подавляется, не перенаправляется, мешает при вызове из воркера/крона.

**12. Слабая схема**
`app/bank_import.py:16-27` — у `postings` нет первичного ключа, нет `FOREIGN KEY` на `accounts` (и `PRAGMA foreign_keys` = 0), нет ни одного индекса по `payment_id`/`account_id` (проверено: в БД только автоиндекс `accounts.number`) — каждый lookup проводки это full scan. В `posting_audit` не сохраняется источник изменения (тот самый `digest`) и кто его внёс — аудит без провенанса.

**13. Весь CSV грузится в память**
`app/bank_import.py:47` — `list(csv.DictReader(fh))` вместо потоковой обработки; `len(rows)` нужен только для прогресс-строки из п.11.

**14. Дубль `payment_id` внутри одного файла молча трактуется как коррекция**
`app/bank_import.py:74-91` — две строки `P-2` на 100 и 200 в одном файле дают баланс 200 и запись в `posting_audit`, как будто это исправление задним числом, а не битая выгрузка. `applied` при этом = 2.

### Housekeeping

`err.log` и `out.md` в корне — пустые untracked файлы, судя по всему артефакты прогона. В `.gitignore` их нет, `.pytest_cache/` и `__pycache__/` тоже не игнорируются.

### Итог

Функционально дифф решает заявленную задачу (дедуп + коррекция с аудитом) и тесты это подтверждают, но три критических дефекта — инъекция, неверная разноска при смене счёта и отсутствие атомарности — делают модуль непригодным для денежного контура в текущем виде. Минимальный набор до мержа: параметризовать запрос на строке 68, снимать сумму со старого счёта при смене `account_id`, обернуть весь файл в одну транзакцию, перейти на `balance = balance + ?` с уникальным индексом, убрать телефон из лога. Хорошей регрессионной страховкой был бы тест на инвариант `balance == SUM(active postings)` — он ловит и находку 2, и находку 4.
