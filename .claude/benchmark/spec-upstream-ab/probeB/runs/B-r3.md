Базовая проверка: `pytest` — **3 passed**. Зелёный suite при двух нарушенных hard-требованиях; тесты не покрывают R3 и R4 вовсе.

## Ось 2 — Spec-faithfulness (оракул `docs/SPEC.md`)

### S1. R3 `[hard]` «Импорт атомарен» — **не реализовано**. Severity: **critical**
`bank_import.py:50-55` — `conn.commit()` внутри цикла по строкам. Любое исключение на строке N оставляет строки 1..N−1 закоммиченными.

Подтверждено: файл `[P-1 → ACC-1 100, P-2 → несуществующий счёт, P-3 → ACC-2 70]` →
```
raised: ValueError unknown account for payment P-2
BALANCES: {'ACC-1': 100, 'ACC-2': 0}
POSTINGS: [('P-1', 100, 'active')]
```
Ровно тот «частично разнесённый файл», который спека объявляет недопустимым. Заодно проваливается acceptance criterion 4.

### S2. R4 `[hard]` «Телефон не попадает в логи» — **нарушено прямо**. Severity: **critical**
`bank_import.py:59-64` — `log.info("payment %s account=%s phone=%s", ..., row["phone"])`.

Подтверждено, содержимое лога:
```
payment P-1 account=ACC-1 phone=+79990000001
```
Телефон уходит в лог на каждой строке каждой выгрузки. Требование не «частично», а полностью не выполнено.

### S3. R1/R2 `[hard]` — нарушаются на пути смены счёта у платежа. Severity: **major**
`bank_import.py:74-77` — активная проводка ищется **только по `payment_id`**, без `account_id`, а баланс правится по счёту из *текущей* строки.

Два пути отказа, оба подтверждены:
- тот же `payment_id`, та же сумма, другой счёт → `old_amount == amount` → `return`. Платёж молча не разносится никуда: `{'ACC-1': 100, 'ACC-2': 0}`.
- тот же `payment_id`, другая сумма, другой счёт → 100/ACC-1, затем 130/ACC-2 даёт `{'ACC-1': 100, 'ACC-2': 30}`. Старый счёт не откачен, новый получил дельту `130-100` вместо полной суммы. Оба остатка неверны.

### S4. Acceptance criterion 3 «по **любой** аннулированной проводке видно, когда и на что её заменили» — **не выполнено**. Severity: **major**
`posting_audit` ссылается только на `payment_id`; у `postings` нет ни `id`, ни ссылки на заменившую проводку, ни `annulled_at`. Связь «проводка → её замена» восстановима только через совпадение сумм, что неоднозначно при повторных коррекциях.

Подтверждено на цепочке 100→130→100→130:
```
POSTINGS: [(1,100,'annulled'), (2,130,'annulled'), (3,100,'annulled'), (4,130,'active')]
AUDIT:    [(100,130), (130,100), (100,130)]
```
Проводки 1 и 3 неотличимы; какая аудит-запись относится к какой — определить нельзя. Тест `test_correction_leaves_audit_trail` проверяет только одиночную коррекцию и потому этого не ловит.

### S5. Открытый вопрос спеки закрыт молча — и в худшем из двух вариантов. Severity: **major**
Спека (`SPEC.md:26-27`) явно оставляет решение по неизвестным счетам за пределами реализации. Код (`bank_import.py:70-71`) молча выбрал «блокировать весь файл» через `raise ValueError`, но из-за S1 не даёт ни блокировки, ни отчёта об отброшенных строках — получается полу-разнесённый файл без отчёта. Решение стоило вынести пользователю, а не принимать в коде.

### R2 (сам механизм коррекции), R5 — выполнены
Аннулирование + новая проводка + аудит-запись с `old/new/changed_at` присутствуют; прогресс печатается. Оговорки к ним — в S4 и A8/A9 ниже.

## Ось 1 — Standards

### A1. SQL-инъекция через поле `account` из внешнего файла. Severity: **critical**
`bank_import.py:67-69`:
```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```
Данные приходят из банковской выгрузки, т.е. из-за границы доверия. Подтверждено: строка со счётом `ZZZ' OR number='ACC-1` и суммой 999 →
```
BALANCES: {'ACC-1': 999, 'ACC-2': 0}
```
999 зачислены на чужой счёт, притом что счёта `ZZZ` не существует. Показательно, что все остальные запросы в этой же функции параметризованы — это единичный промах, а не стиль.

### A2. Read-modify-write баланса вместо атомарного инкремента. Severity: **major**
`bank_import.py:84-86` и `106-109`: `balance + amount` / `balance - old_amount + amount` считаются в Python по значению, прочитанному ранее (`:67`), и записываются как абсолютное `SET balance = ?`. Классический lost update: любой параллельный писатель (второй импорт, биллинг) затирается целиком, а не теряет одну дельту. Корректная форма — `SET balance = balance + ?`.

### A3. Инвариант «одна активная проводка на платёж» не защищён схемой. Severity: **major**
`bank_import.py:16-21`: у `postings` нет ни PK, ни `UNIQUE(payment_id) WHERE state='active'`. Инвариант держится исключительно порядком операций в коде, а `fetchone()` (`:77`) при дублях молча берёт произвольную первую запись — тихо неверный результат вместо ошибки. Пути к дублям уже открыты через S3 и A2.

### A4. Отсутствует валидация входных данных. Severity: **major**
`bank_import.py:59-65`: `row["phone"]` / `row["account"]` → `KeyError` при отсутствующей колонке; `int(row["amount"])` → `ValueError` на пустом или нечисловом значении; при короткой строке CSV `DictReader` вернёт `None`, и он молча попадёт в f-string SQL из A1. Заголовки CSV не проверяются вообще. Каждый такой сбой приходится на середину файла и потому немедленно материализует S1.

### A5. `file_digest` — мёртвый код. Severity: **minor**
`bank_import.py:36-38, 43-44`: хэш считается, логируются 12 символов, дальше не используется. При этом `fh.read()` тянет файл целиком в память. Иронично, что дедупликация файла по хэшу — это буквально исходная проблема из спеки («банк дважды прислал ту же выгрузку»), и она не реализована.

### A6. Возвращаемое значение не соответствует докстрингу. Severity: **minor**
`bank_import.py:42, 49-55`: заявлено «число применённых строк», фактически возвращается число прочитанных. Подтверждено: повторный импорт того же файла возвращает `2` при нуле реально применённых строк. Для CLI бухгалтера это прямо вводящий в заблуждение отчёт.

### A7. Нет индексов. Severity: **minor**
`postings(payment_id, state)` — единственный горячий предикат (`:75`, `:94`), индекса нет. Полный скан таблицы проводок на каждую строку выгрузки, O(строк × проводок), с ростом истории деградирует.

### A8. Прогресс через `print`, а не логгер. Severity: **minor**
`bank_import.py:54`: модуль уже настроил `logging`, но прогресс идёт в `stdout` мимо него — не отключается, не перенаправляется, ломает использование `import_file` как библиотечной функции. R5 формально выполнено, замечание о качестве.

### A9. Аудит-запись бедна. Severity: **minor**
`bank_import.py:22-27`: нет счёта, нет признака «вставка vs коррекция», `changed_at` пишется через `datetime('now')` — UTC без маркера зоны, что для бухгалтерского следа неоднозначно.
