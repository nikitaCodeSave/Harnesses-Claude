# Ревью `app/bank_import.py` (незакоммиченный дифф)

## CRITICAL

### 1. SQL-инъекция через колонку `account` — `app/bank_import.py:67-69`
```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```
Единственное место в файле, где параметризация не используется — и именно оно принимает недоверенные данные из файла банка. Подтверждено запуском: строка CSV со счётом `' UNION SELECT id, 999999 FROM accounts WHERE number='ACC-1` при **несуществующем счёте** не отклоняется, а проводится — баланс `ACC-1` стал `1000000`.

Побочно ломается и на легитимных данных: счёт `O'BRIEN` → `OperationalError: near "BRIEN": syntax error`. То есть это не только вектор атаки, но и баг на обычной кавычке.

### 2. R3 (атомарность) нарушен — `app/bank_import.py:52`
`conn.commit()` стоит **внутри** цикла по строкам. Спека R3 `[hard]`: «применён целиком либо не применён вовсе». Подтверждено: файл из 4 строк с битым счётом в 3-й → `ValueError`, но в БД остались 2 проводки и балансы `ACC-1=100, ACC-2=250`. Ровно то полу-разнесённое состояние, которое запрещает R3 и AC4. Нет ни оборачивающей транзакции, ни `rollback` в обработчике.

### 3. R4 (PII) нарушен — `app/bank_import.py:59-64`
```python
log.info("payment %s account=%s phone=%s", ..., row["phone"])
```
Спека R4 `[hard]`: телефон клиента не попадает в логи. Подтверждено захватом лога: `payment P-1 account=ACC-1 phone=+79990000001`. Поле `phone` в коде вообще больше нигде не используется — оно читается исключительно ради того, чтобы утечь в лог.

### 4. Коррекция по платежу, пришедшему на другой счёт, портит балансы обоих счетов — `app/bank_import.py:74-77, 106-109`
Поиск существующей проводки идёт только по `payment_id`, без `account_id`, а пересчёт `balance - old_amount + amount` применяется к **новому** счёту. Подтверждено: `P-1` на `ACC-1` = 100, затем тот же `P-1` приходит на `ACC-2` с суммой 130 → `ACC-1` остаётся **100** (хотя его проводка аннулирована), `ACC-2` получает **30** вместо 130. Оба баланса неверны, расхождение с реестром проводок молчаливое. Сценарий реалистичен: банк исправляет не только сумму, но и реквизиты.

## MAJOR

### 5. Идемпотентность держится только на коде, не на схеме — `app/bank_import.py:16-21`
У `postings` нет ни первичного ключа, ни частичного уникального индекса вида `UNIQUE(payment_id) WHERE state='active'`. При двух активных проводках на один `payment_id` (гонка, ручная правка, будущий баг) `fetchone()` на строке 77 молча возьмёт произвольную из них и продолжит считать баланс. Ключевой инвариант R1 ничем не защищён на уровне хранилища.

### 6. `file_digest` вычисляется и выбрасывается — `app/bank_import.py:36-38, 43-44`
Хеш файла считается, логируются первые 12 символов, и на этом всё: он нигде не сохраняется и ни с чем не сверяется. Исходная проблема из спеки — «банк дважды прислал один и тот же файл» — на уровне файла не решена вообще; работает только идемпотентность по `payment_id`. Полуреализованная фича, которая читается как готовая защита.

### 7. Возвращаемое значение врёт — `app/bank_import.py:49-55`
Docstring: «Возвращает число применённых строк». `applied` инкрементируется для каждой строки, включая no-op-ветку `old_amount == amount` (строки 90-91). Подтверждено: повторный импорт того же файла возвращает `2`, применив ноль строк. Для бухгалтера это прямая дезинформация в CLI-выводе.

### 8. Нет валидации входного файла — `app/bank_import.py:58-72`
`row["phone"]`, `row["account"]`, `int(row["amount"])` — без проверок. Подтверждено: CSV без колонки `phone` → `KeyError: 'phone'`; сумма `12.50` → `ValueError: invalid literal for int()`. Оба падения происходят **после** того, как предыдущие строки уже закоммичены (см. #2). Ни заголовок, ни типы не проверяются до начала записи в БД.

## MINOR

### 9. Read-modify-write баланса — `app/bank_import.py:72, 85, 107-108`
Баланс читается в Python и записывается вычисленным значением вместо `SET balance = balance + ?`. При двух параллельных импортах — потеря обновления. По спеке запуск ручной и одиночный, так что риск сейчас низкий, но правка бесплатна и снимает целый класс проблем.

### 10. Нет индекса на `postings.payment_id` — `app/bank_import.py:16-21`
Каждая строка выгрузки делает полный скан таблицы проводок, которая растёт монотонно. Квадратичное поведение на горизонте месяцев.

### 11. Смешение каналов вывода — `app/bank_import.py:44, 54, 59`
`print()` для прогресса (R5 это допускает) соседствует с `log.info` — вывод расползается по двум каналам с разной судьбой. Плюс INFO-запись на каждую строку файла — лог зашумлён.

### 12. Файл целиком в память дважды — `app/bank_import.py:38, 47`
`fh.read()` в `file_digest` и `list(csv.DictReader(fh))`. Для дневной выгрузки приемлемо, но `DictReader` и так итератор — материализация нужна только ради `len(rows)` в прогресс-строке.

### 13. Открытый вопрос спеки решён молча — `app/bank_import.py:70-71`
`docs/SPEC.md:26-27` явно фиксирует нерешённым: неизвестный счёт — отбрасывать с отчётом или блокировать файл. Код выбрал «блокировать» (`raise ValueError`), без пометки в коде или спеке. Причём в связке с #2 получился худший вариант: файл блокируется **и** оставляет частичное состояние.

### 14. Аудит не привязан к конкретной проводке — `app/bank_import.py:22-27`
AC3 требует «по любой аннулированной проводке увидеть, когда и на что её заменили». `posting_audit` ссылается только на `payment_id` и суммы; у `postings` нет идентификатора. При двух коррекциях подряд (100→130→150) связь восстанавливается лишь сопоставлением сумм и времени. Тест `test_correction_leaves_audit_trail` этот случай не покрывает.

---

**Вне диффа, к сведению:** в git отслеживаются `__pycache__/*.pyc` — они всплывают в `git status` при каждом прогоне тестов. Не трогал, это досталось от предыдущего коммита.

**Общая картина.** Три `[hard]`-ограничения спеки из четырёх (R3, R4 и — через #4 — R2) нарушены, плюс инъекция. При этом весь тестовый набор зелёный: тесты проверяют только успешные сценарии на чистых данных, ни один не проверяет сбой в середине файла, отсутствие PII в логах и невалидный вход. Это и есть основная причина, почему код выглядит готовым.
