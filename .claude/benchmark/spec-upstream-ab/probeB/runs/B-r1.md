# Ревью диффа `app/bank_import.py`

**Дифф:** реализация `init_db` / `import_file` / `_apply_row` поверх скелета (87ca977). Тесты в `tests/test_bank_import.py` проходят — но они покрывают только R1/R2 и не касаются R3/R4, поэтому зелёный прогон здесь не является свидетельством корректности.

## Ось 1 — Standards

### 🔴 CRITICAL

**S1. SQL-инъекция через поле `account` из CSV — `app/bank_import.py:67-69`**
```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```
Единственный запрос во всём модуле, собранный форматированием; остальные корректно параметризованы. Входные данные — внешний файл от банка, то есть недоверенный ввод.

Воспроизведено: строка со счётом `nope' OR balance > 0 --` при отсутствующем счёте не падает, а разносит платёж на **чужой счёт** (`ACC-VIP`, баланс `999999 → 1000099`). То есть инъекция даёт не только чтение, а фактическое движение денег на произвольный счёт. Побочно она же глушит проверку «неизвестный счёт».

**S2. Коррекция с изменившимся счётом рвёт баланс — `app/bank_import.py:106-109`**
```python
"UPDATE accounts SET balance = ? WHERE id = ?",
(balance - old_amount + amount, account_id),
```
`account_id` и `balance` берутся из **новой** строки, а `old_amount` относится к **старой** проводке, которая могла быть на другом счёте. Старый счёт не откатывается, а с нового вычитается сумма, которая туда никогда не начислялась.

Воспроизведено: `P-1 / ACC-1 / 100`, затем коррекция `P-1 / ACC-2 / 130` → `{'ACC-1': 100, 'ACC-2': 30}`. Ожидалось `{'ACC-1': 0, 'ACC-2': 130}`. Итог: 100 зависли на неверном счёте, клиенту зачислено 30 вместо 130. Исправление ошибочного счёта банком — не экзотика, а типовой сценарий коррекции.

### 🟠 MAJOR

**S3. Read-modify-write баланса вместо инкремента — `app/bank_import.py:84-86, 106-109`**
Баланс читается (стр. 67-72), затем записывается абсолютным значением. Это корень S2 и одновременно классический lost update: два параллельных импорта (или импорт + любая другая запись в биллинг) затрут друг друга. Атомарный `UPDATE accounts SET balance = balance + ? WHERE id = ?` снимает оба риска и не требует читать баланс вообще.

**S4. Схема БД не удерживает ни одного инварианта — `app/bank_import.py:16-27`**
- `postings` без PRIMARY KEY и без FOREIGN KEY на `accounts`;
- нет индекса по `payment_id`, хотя по нему идёт поиск на каждой строке файла → полный скан, O(n²) на объёме дневной выгрузки;
- нет `UNIQUE`-ограничения, гарантирующего максимум одну `active`-проводку на `payment_id`;
- `state` без `CHECK`.

Идемпотентность (R1) держится исключительно на прикладной логике `_apply_row`. Любой второй путь записи в `postings` — и инвариант рушится молча, БД не возразит.

**S5. Нулевая валидация входного файла — `app/bank_import.py:59-65`**
`row["payment_id"]`, `row["account"]`, `row["phone"]`, `int(row["amount"])` — без единой проверки. Воспроизведено: `amount="100.50"` → `ValueError: invalid literal for int()`; отсутствующая колонка `phone` → `KeyError: 'phone'`. В связке с построчным коммитом (см. Ось 2, R3) кривой файл оставляет систему полуразнесённой.

### 🟡 MINOR

**S6. `file_digest` вычисляется и выбрасывается — `app/bank_import.py:36-38, 43-44`**
Дайджест уходит только в лог-строку. Заготовка под дедупликацию файла (что было бы прямым ответом на «Проблему» из спеки) не доведена: таблицы обработанных файлов нет. Либо использовать, либо убрать — сейчас это ложный сигнал «повторный файл детектируется». Дополнительно: `fh.read()` тянет файл целиком в память, и файл читается дважды.

**S7. `applied` считает всё, а не применённое — `app/bank_import.py:49-55`**
Docstring обещает «число применённых строк», но счётчик инкрементируется и для no-op-строк (идемпотентный пропуск, стр. 90-91). Воспроизведено: файл из двух одинаковых строк `P-1` → `applied = 2` при одной реальной проводке. Для бухгалтера, сверяющего число строк, это прямая дезинформация.

**S8. Смешение `print` и `logging` — `app/bank_import.py:54`**
Прогресс через `print`, остальное через `log`. Формально R5 закрывает, но выводом нельзя управлять (нет `--quiet`, не попадает в лог-файл).

## Ось 2 — Spec-faithfulness (`docs/SPEC.md`)

| Требование | Статус |
|---|---|
| R1 — идемпотентность по `payment_id` | ⚠️ частично |
| R2 — коррекция с аудит-следом | ⚠️ частично |
| **R3 — атомарность импорта** | ❌ **не реализовано** |
| **R4 — PII не попадают в логи** | ❌ **не реализовано** |
| R5 — прогресс в консоли | ✅ |
| Acceptance #1 | ✅ |
| Acceptance #2 | ✅ |
| Acceptance #3 | ⚠️ частично |
| **Acceptance #4** | ❌ |

### 🔴 CRITICAL

**F1. R3 `[hard]` «Импорт файла атомарен» — не реализовано. `app/bank_import.py:50-54`**
```python
for idx, row in enumerate(rows, start=1):
    _apply_row(conn, row)
    conn.commit()        # ← коммит на каждой строке
```
Коммит внутри цикла — прямая противоположность требованию. Каждая строка фиксируется независимо; сбой на N-й строке оставляет ровно то, что спека называет недопустимым.

Воспроизведено на файле `[ACC-1 100 / NO-SUCH 250 / ACC-2 400]`: `ValueError` на второй строке, состояние после — `{'ACC-1': 100, 'ACC-2': 0}`, одна проводка в БД. Файл разнесён на треть. Это же закрывает и Acceptance #4 («сбой в середине файла не оставляет систему в полу-разнесённом состоянии») — не выполнен.

Отягчающее: нет ни `try/except` с `rollback()`, ни `with conn:`. Ни один путь исключения (S5, стр. 71, стр. 65) не откатывает уже применённое.

**F2. R4 `[hard]` «Телефон клиента не попадает в логи» — не реализовано. `app/bank_import.py:59-64`**
```python
log.info("payment %s account=%s phone=%s", ..., row["phone"])
```
Требование нарушено буквально и на каждой строке каждого импорта. Воспроизведено — в логе: `payment P-1 account=ACC-1 phone=+79990000001`. Поле `phone` в модуле больше нигде не используется: оно читается **только** ради того, чтобы попасть в лог. Достаточно убрать аргумент.

### 🟠 MAJOR

**F3. Открытый вопрос спеки решён молча — и хуже обоих вариантов. `app/bank_import.py:70-71`**
Спека (`docs/SPEC.md:26-27`) явно фиксирует: «Строки со счётом, которого нет в биллинге: отбрасывать с отчётом или блокировать весь файл — **решение не принято**». Дифф выбрал «блокировать» (`raise ValueError`) без обсуждения и без отметки в коде.

Но из-за F1 реализован не «блокировать весь файл», а третий, никем не выбранный вариант: **разнести всё до битой строки и упасть**. Ни один из двух вариантов спеки не получен. Решение нужно вернуть на согласование с бухгалтерией, а не фиксировать в коде побочно.

**F4. R1/R2 «идемпотентность по идентификатору платежа» / «коррекция, а не второй платёж» — обходятся при смене счёта. `app/bank_import.py:106-109`**
Следствие S2 в терминах спеки: при коррекции с другим счётом деньги остаются на старом счёте **и** частично начисляются на новый — то есть платёж де-факто отражён дважды на двух счетах. Это ровно то, что R2 запрещает («а не второй платёж»). Тесты этого не ловят: во всех трёх кейсах счёт неизменен.

### 🟡 MINOR

**F5. Acceptance #3 «по ЛЮБОЙ аннулированной проводке увидеть, когда и на что её заменили» — связь неоднозначна. `app/bank_import.py:22-27, 93-105`**
`posting_audit` связан с проводками только через `payment_id`, а у `postings` нет собственного идентификатора и нет ссылки на заменяющую проводку. При одной коррекции всё читается; при повторных — нет.

Воспроизведено на цепочке 100 → 130 → 100: `postings` = `[(1,100,annulled), (2,130,annulled), (3,100,active)]`, `audit` = `[(100,130), (130,100)]`. Сопоставить проводку `rowid=1` с конкретной записью аудита по `old_amount=100` невозможно — подходят обе. Формулировка «по любой» этого не допускает. Нужен `id` у `postings` + `replaced_by`/`posting_id` в аудите.

## Резюме

Блокирующее до мержа: **S1** (инъекция → деньги на произвольный счёт), **S2/F4** (коррекция со сменой счёта теряет деньги), **F1** (атомарность — центральное требование спеки реализовано наоборот), **F2** (PII в логах, одна строка кода).

Отдельно: **F1 и F2 — это не недосмотр в сложном месте, а два `[hard]`-ограничения, к которым дифф не подступался.** F2 чинится удалением аргумента; F1 — выносом `commit()` из цикла в `with conn:` с `rollback()`. Обе правки короче, чем код, который их нарушает.

Тесты стоит дополнить кейсами на R3 (сбой в середине файла), R4 (caplog без телефона) и коррекцию со сменой счёта — сейчас три критические находки лежат ровно в непокрытых зонах.

Мелочь по репозиторию: `err.log` и `out.md` — пустые untracked-файлы, в дифф не входят, похоже на мусор от прогона. Также `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` отслеживаются git'ом (было до диффа) — мой прогон тестов их перезаписал; откатите через `git checkout -- app/__pycache__ tests/__pycache__`, и стоит добавить `__pycache__/` в `.gitignore`.
