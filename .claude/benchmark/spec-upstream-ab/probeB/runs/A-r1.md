# Ревью диффа: `app/bank_import.py`

Дифф реализует скелет импорта из `docs/SPEC.md`. Все 3 существующих теста зелёные — но они покрывают только R1/R2 и не ловят ни одного из трёх critical-нарушений ниже. Каждую находку проверял исполнением, вывод привожу.

## Critical

### 1. R3 нарушен: commit на каждой строке → частично разнесённый файл
**`app/bank_import.py:52`** (`conn.commit()` внутри цикла)

SPEC R3 `[hard]`: «Импорт файла атомарен: применён целиком либо не применён вовсе». Код коммитит каждую строку отдельно, а `_apply_row` кидает `ValueError` на неизвестном счёте (`:71`). Обработки исключения и `rollback` нет нигде.

Файл из 4 строк, сбой на 3-й:
```
raised: ValueError unknown account for payment P-3
balances after failure: {'ACC-1': 100, 'ACC-2': 250}   # ожидалось 0/0
postings in DB: 2                                       # ожидалось 0
```
Это ровно то состояние, которое R3 запрещает, и оно необратимо: повторный запуск исправленного файла пройдёт по строкам 1–2 как «идемпотентный», а бухгалтер не узнает, что часть дня уже разнесена. Нужен один транзакционный контекст на весь файл (`with conn:` / явный BEGIN + rollback), а не per-row commit.

### 2. SQL-инъекция: номер счёта из CSV клеится в запрос f-строкой
**`app/bank_import.py:67-69`**

```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```
Единственное место в файле, где не используется параметризация — все остальные запросы написаны правильно, что делает это похожим на недосмотр, а не на осознанный выбор.

Данные приходят из внешнего файла банка (недоверенный вход). Строка `' OR number='ACC-VICTIM` в колонке `account`:
```
balances: {'ACC-1': 0, 'ACC-VICTIM': 1099}   # платёж разнесён на счёт, не названный в файле
```
То есть подделанная выгрузка позволяет зачислить деньги на произвольный счёт. Плюс тот же баг ломает легитимные данные — счёт с апострофом падает:
```
raised: OperationalError near "BRIEN": syntax error
```
Исправление: параметризовать как в соседних запросах (`WHERE number = ?`).

### 3. R4 нарушен: телефон клиента пишется в лог
**`app/bank_import.py:59-64`**

SPEC R4 `[hard]`: «Персональные данные из выгрузки (телефон клиента) не попадают в логи». Код логирует `phone=%s` на каждой строке:
```
log: 'payment P-1 account=ACC-1 phone=+79990000001'
```
`phone` в этой функции больше нигде не используется — он читается исключительно ради лога. Утечка PII необратима после того, как логи уехали в хранилище/агрегатор.

## Major

### 4. Смена счёта у разнесённого платежа портит балансы обоих счетов
**`app/bank_import.py:74-77`, `106-109`**

Идемпотентность/коррекция определяются только по `payment_id`; `account_id` из существующей проводки не читается. Если банк прислал платёж с исправленными реквизитами:

* та же сумма, другой счёт → срабатывает ранний `return` на `:91`, изменение молча игнорируется (деньги остаются на старом счёте, аудит-следа нет):
  ```
  ACC-1 -> ACC-2, сумма 100: balances {'ACC-1': 100, 'ACC-2': 0}   # ожидалось 0/100
  ```
* другой счёт + другая сумма → сторно не выполняется на старом счёте, а новый уменьшается на сумму, которую он никогда не получал:
  ```
  ACC-1 -> ACC-2, 100 -> 130: balances {'ACC-1': 100, 'ACC-2': 30}  # ожидалось 0/130
  ```
  `balance - old_amount + amount` на строке `:108` считается по балансу **нового** счёта, а `old_amount` относится к **старому**. Оба счёта в итоге неверны.

### 5. Инвариант «одна активная проводка на платёж» не закреплён в схеме
**`app/bank_import.py:16-21`**

Вся логика идемпотентности держится на предположении, что `fetchone()` на `:74` вернёт не более одной активной проводки, но в схеме нет ни уникального (частичного) индекса на `payment_id WHERE state='active'`, ни PK, ни FK на `accounts(id)`, ни индекса вообще. Последствия: (а) если инвариант когда-либо нарушится (гонка, ручная правка, баг выше), `UPDATE ... state='annulled'` на `:93` аннулирует *все* активные проводки, а из баланса вычтется только одна `old_amount` — расхождение без единой ошибки в логах; (б) поиск по `payment_id` — полный скан, импорт квадратичен по размеру файла.

Отдельно: `state` — свободный TEXT без CHECK-ограничения; опечатка в значении тихо создаст «невидимую» проводку.

### 6. Тесты не покрывают ни одного hard-ограничения, которое нарушено
**`tests/test_bank_import.py`**

Три теста проверяют R1 (повтор файла), R2 (коррекция) и критерий 3 (аудит). Нет тестов на R3 (сбой в середине файла) и R4 (отсутствие PII в логах) — то есть именно на те требования, которые в диффе нарушены. Зелёный прогон здесь читается как «готово», хотя два hard-ограничения из четырёх не выполнены. Нужны тест на rollback при сбое в середине файла (через `caplog`/`assert` по балансам) и тест, что телефон не появляется в записях лога.

## Minor

### 7. `file_digest` вычисляется и выбрасывается
**`app/bank_import.py:36-38, 43-44`**

Хеш файла считается, логируются первые 12 символов — и всё. Нигде не хранится и не проверяется. При этом исходная проблема из SPEC («банк дважды прислал одну и ту же выгрузку») — это ровно тот случай, для которого реестр обработанных дайджестов был бы естественной защитой. Сейчас это либо незаконченный замысел, либо мёртвый код; в текущем виде — расход на чтение файла целиком в память без пользы.

### 8. Аудит-след неоднозначен при повторных коррекциях
**`app/bank_import.py:22-27`, `97-105`**

У `postings` нет собственного id, а `posting_audit` ссылается только на `payment_id`. Критерий 3 SPEC («по любой аннулированной проводке увидеть, когда и на что её заменили») выполняется, только пока сумма коррекции уникальна. Цепочка 100 → 130 → 100 → 130 даёт:
```
postings: [('P-1',100,'annulled'), ('P-1',130,'annulled'), ('P-1',100,'annulled'), ('P-1',130,'active')]
audit:    [(100,130), (130,100), (100,130)]
```
Сопоставить конкретную аннулированную проводку с её аудит-записью нельзя — совпадающие пары неразличимы. Лечится id у `postings` и ссылками `old_posting_id`/`new_posting_id` в аудите.

### 9. Нет валидации строки CSV — падение вместо внятной ошибки
**`app/bank_import.py:59-65`**

`int(row["amount"])` падает на дробной сумме (`ValueError: invalid literal for int() with base 10: '100.50'`), а `row["phone"]`/`row["account"]` дают `KeyError`, если банк изменил набор колонок. Само по себе падение допустимо (fail fast), но в связке с находкой №1 каждое такое падение оставляет файл полуразнесённым. Стоит проверять заголовок CSV до начала разноски.

### 10. Мелочи качества
* **`:85`, `:106-108`** — баланс пишется как read-modify-write из Python (`balance + amount`) вместо `SET balance = balance + ?`. В однопоточном CLI это работает, но делает потерю обновления возможной при любом параллельном писателе и лишает БД возможности защитить инвариант.
* **`:54`** — прогресс через `print()`, всё остальное через `logging`. R5 формально выполнен, но два канала вывода в одном модуле; `print` не подавить и не перенаправить стандартными средствами.
* **`:103`** — `datetime('now')` пишет UTC без указания зоны в текстовое поле; при чтении бухгалтером время будет интерпретировано как локальное.
* **`:71`** — открытый вопрос SPEC («отбрасывать строку с неизвестным счётом или блокировать файл») решён в пользу «блокировать», но решение не зафиксировано ни в SPEC, ни в комментарии. Стоит либо согласовать, либо явно отметить как принятое.

### 11. Гигиена репозитория
`err.log` и `out.md` — пустые untracked-файлы в корне. Кроме того, `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` **отслеживаются git'ом** — их стоит удалить из индекса и добавить в `.gitignore`.
