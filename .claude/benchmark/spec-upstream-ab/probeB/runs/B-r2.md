# Ревью диффа `app/bank_import.py`

Тесты (`3 passed`) проходят — но покрывают только happy-path: один счёт, коррекция на том же счёте, без сбоев. Все находки ниже подтверждены реальным прогоном, не чтением.

---

## Ось 1 — Standards

### S1 · CRITICAL · SQL-инъекция — `app/bank_import.py:67-68`
```python
f"SELECT id, balance FROM accounts WHERE number = '{row['account']}'"
```
Единственный запрос в файле, где значение из внешнего CSV подставляетсяف-строкой; все остальные 6 запросов параметризованы — то есть это не стиль модуля, а промах.

Подтверждено: строка со счётом `nope' OR number='ACC-2` разнесла платёж на **чужой счёт** — `ACC-2: 999 → 1099`, при том что счёта `nope` не существует. Легитимный счёт с апострофом (`O'Brien`) роняет импорт с `OperationalError: near "Brien": syntax error`. Источник данных — файл от банка, то есть внешний ввод, а последствие — деньги не на том счёте.

### S2 · MAJOR · Коррекция со сменой счёта разрушает балансы — `:106-109`
`existing` (`:74-77`) выбирает только `amount`, но не `account_id` аннулируемой проводки. При откате вычитается `old_amount` из баланса **нового** счёта, а старый счёт не трогается вовсе.

Подтверждено: `P-1` разнесён на `ACC-1` (100), затем повторно пришёл на `ACC-2` с суммой 130 →
`{'ACC-1': 100, 'ACC-2': 30}` вместо `{'ACC-1': 0, 'ACC-2': 130}`. У одного клиента фантомные 100, у второго недостача 100. Суммарный итог сходится, поэтому сверка по тоталу это не поймает.

### S3 · MAJOR · Идемпотентность держится только на прикладной проверке — `SCHEMA :16-21`, `:72,85,106-109`
В схеме нет ни уникального индекса на активную проводку (`UNIQUE INDEX ON postings(payment_id) WHERE state='active'`), ни FK `postings.account_id → accounts.id`. Баланс пишется как read-modify-write (`balance + amount` посчитан в Python), а не `SET balance = balance + ?`.

Два одновременных импорта (второй терминал, двойной запуск нетерпеливым бухгалтером) оба увидят `existing is None` и оба вставят проводку → двойное списание. Это ровно тот инцидент, из-за которого спека написана, и на уровне БД от него нет ни одного барьера.

### S4 · MINOR · `file_digest` — мёртвый код — `:36-38, 43-44`
Дайджест считается (полное чтение файла в память отдельным проходом), пишется в лог обрезанным до 12 символов и больше нигде не используется: не сохраняется, не сверяется. Это заготовка под дедупликацию файлов, которой не случилось.

### S5 · MINOR · `applied` врёт — `:49-55`
Docstring обещает «число применённых строк», но счётчик инкрементируется и для no-op-строк. Подтверждено: повторный прогон того же файла возвращает `1`, хотя применено `0`. Именно по этому числу бухгалтер судит, что произошло.

### S6 · MINOR · Прогресс через `print` — `:54`
В модуле настроен `log`, но прогресс идёт в stdout мимо него: нельзя заглушить, нельзя перенаправить, засоряет вывод тестов.

### S7 · MINOR · Нет валидации входного CSV — `:59-65`
Отсутствующая колонка → голый `KeyError`; пустой или дробный `amount` (`"100.50"`) → `ValueError` из `int()`. Ни одно сообщение об ошибке не содержит номер строки файла — бухгалтеру не с чем идти к банку.

## Ось 2 — Spec-faithfulness (оракул — `docs/SPEC.md`)

### R3 `[hard]` · **НЕ ВЫПОЛНЕНО** · CRITICAL — `:52`
> *Импорт файла атомарен: применён целиком либо не применён вовсе. Частично разнесённый файл недопустим.*

`conn.commit()` стоит **внутри** цикла по строкам. Нет ни транзакционной границы на файл, ни `rollback()` в обработчике исключения — обработчика вообще нет.

Подтверждено: файл из 4 строк, 3-я ссылается на несуществующий счёт → `ValueError`, но первые две строки закоммичены и переживают явный `rollback()`: `{'ACC-1': 100, 'ACC-2': 250}`, 2 проводки в БД. Это буквально то состояние, которое спека называет недопустимым. Так же ломается AC4.

### R4 `[hard]` · **НЕ ВЫПОЛНЕНО** · CRITICAL — `:59-64`
> *Персональные данные из выгрузки (телефон клиента) не попадают в логи.*

`log.info("payment %s account=%s phone=%s", ..., row["phone"])` — телефон логируется на уровне INFO для **каждой** строки. Захваченный лог: `payment P-1 account=ACC-1 phone=+79990000001`. Требование нарушается всегда, а не на краевом пути.

### R2 `[hard]` · **ВЫПОЛНЕНО ЧАСТИЧНО** · MAJOR — `:93-109`, `SCHEMA :16-27`
> *Коррекция с аудит-следом (что было, что стало, когда), а не второй платёж.*

Механика аннулирования и записи в `posting_audit` есть, но AC3 («по **любой** аннулированной проводке увидеть, когда и на что её заменили») не достигается: у `postings` нет идентификатора проводки, а `posting_audit` связан с ней только по `payment_id`. Подтверждено на цепочке 100 → 130 → 100:

```
postings: [(1, 100, 'annulled'), (2, 130, 'annulled'), (3, 100, 'active')]
audit   : [(100, 130, '2026-07-22 16:45:36'), (130, 100, '2026-07-22 16:45:36')]
```
Две аннулированные проводки, две записи аудита, `changed_at` совпадает до секунды — сопоставить конкретную проводку с её заменой невозможно. Плюс на пути со сменой счёта коррекция даёт неверные балансы (см. S2).

### R1 `[hard]` · **ВЫПОЛНЕНО ПО ОДНОПОТОЧНОМУ ПУТИ** · MAJOR
> *Разноска платежа идемпотентна по идентификатору платежа.*

Логика `:74-91` корректна, тест `test_repeated_file_does_not_double_charge` проходит. Но гарантии нет ни на одном другом пути: при конкурентном запуске идемпотентность отсутствует (S3), а через инъекцию в поле счёта тот же платёж можно разнести на другой счёт (S1). По вашему критерию «нарушается на каком-то пути исполнения» — требование не закрыто.

### R5 `[soft]` · ВЫПОЛНЕНО — `:54`
Прогресс `[idx/total] payment_id` печатается. Замечание к каналу вывода — S6, но само требование закрыто.

### Открытый вопрос спеки · MINOR — `:70-71`
> *Строки со счётом, которого нет в биллинге: отбрасывать с отчётом или блокировать весь файл — решение не принято.*

Дифф молча выбрал «блокировать» (`raise ValueError`) — решение не согласовано. Хуже того, в связке с нарушением R3 не получается **ни один** из двух вариантов: файл не блокируется (часть строк уже применена) и строка не отбрасывается с отчётом. Реализован третий, худший вариант.

### NON-GOALS — чисто
Ни S3-автозапуска, ни других банков, ни изменений API биллинга. Скоуп диффа не разъехался.
