# Ось 1 — Standards

### 1. CRITICAL — смена счёта у платежа рассыпает балансы
`app/bank_import.py:67-94`

`existing` выбирает только `id, amount` и сравнивает **только сумму**. Если тот же `payment_id` приходит повторно с исправленным счётом, коррекция применяется к *новому* счёту дельтой `amount - old_amount`, а старый счёт никто не откатывает.

```
day1:  P-1 → ACC-1, 100
fix:   P-1 → ACC-2, 130
факт:  ACC-1=100, ACC-2=30      ожидалось: ACC-1=0, ACC-2=130
postings: (1,P-1,acc=1,100,annulled), (2,P-1,acc=2,130,active)
```

Активная проводка говорит «130 на ACC-2», а баланс ACC-2 = 30. Деньги остались на счёте чужого клиента — ровно тот класс ущерба, ради которого спека написана.

### 2. MAJOR — смена счёта без смены суммы = молчаливый no-op
`app/bank_import.py:83-84`

`if old_amount == amount: return False` — банк переприслал платёж с исправленным счётом, сумма та же → код не делает ничего, проводка навсегда остаётся на неправильном счёте, `applied` возвращает 0, ни лога, ни ошибки. Проверено: `ACC-1=100, ACC-2=0`, `postings` не изменились.

### 3. MAJOR — `rollback()` уничтожает незакоммиченные данные вызывающего
`app/bank_import.py:41, 47-48`

`conn.execute("BEGIN")` падает с `OperationalError: cannot start a transaction within a transaction`, если вызывающий код уже держит открытую транзакцию. Дальше `except Exception` делает `conn.rollback()` — и откатывает **чужие** изменения, которых функция не касалась. Проверено: вставленная до вызова строка `ACC-NEW` исчезла. Функция не владеет соединением, но управляет его транзакцией как своей.

### 4. MINOR — инвариант «одна active-проводка на платёж» держится только кодом
`app/bank_import.py:15-22 (SCHEMA), :67`

Нет `UNIQUE`-ограничения (частичного индекса по `payment_id WHERE state='active'`), а выборка идёт через `fetchone()` без `ORDER BY`. Появись вторая active-строка — код молча возьмёт произвольную и «скорректирует» не ту.

### 5. MINOR — `FOREIGN KEY` декоративен
`app/bank_import.py:18`, `init_db`

`PRAGMA foreign_keys` = 0 (проверено), `init_db` его не включает — `REFERENCES accounts(id)` не проверяется вообще.

### 6. MINOR — диагностика без привязки к строке файла
`app/bank_import.py:57, 64`

`int(row["amount"])` на реалистичной банковской сумме `100.50` роняет весь импорт с `ValueError: invalid literal for int() with base 10: '100.50'` — без номера строки и без `payment_id`. То же у `unknown account for payment P-2` — нет ни номера строки, ни самого номера счёта. Пользователь — бухгалтер из CLI, чинить ему нечего.

### 7. MINOR — мелочи
- `list(csv.DictReader(fh))` (`:37`) держит выгрузку целиком в памяти.
- `print` прогресса (`:45`) печатается для строк, которые затем откатываются — на упавшем импорте пользователь видит «применено» для того, чего в базе нет.

# Ось 2 — Spec-faithfulness

### R2 + Acceptance 3 — CRITICAL, не реализовано
`app/bank_import.py:9-23 (SCHEMA), :86-90`

R2 требует аудит-след «что было, **что стало, когда**»; Acceptance 3 — «по любой аннулированной проводке увидеть, **когда** и **на что** её заменили». В схеме `postings` есть только `id, payment_id, account_id, amount, state`. Нет ни одной временной колонки и нет ссылки на заменяющую проводку.

«Когда» — отсутствует полностью, восстановлению не подлежит. «На что» — при цепочке коррекций неопределимо:

```
postings: (1,P-1,100,annulled) (2,P-1,130,annulled) (3,P-1,100,annulled) (4,P-1,130,active)
```

По проводке `id=1` нельзя сказать, заменила её `id=2` или `id=3`. Требование выглядит закрытым (`state='annulled'` есть, тест зелёный), но не выполнено ни на одном пути.

### R3 — MAJOR, нарушается на реальном пути
`app/bank_import.py:47`

`except Exception` не ловит `KeyboardInterrupt`. Пользователь по спеке — «бухгалтер, запускает импорт руками из CLI»; Ctrl+C посреди файла — штатный сценарий. Проверено:

```
KeyboardInterrupt пролетел мимо except Exception
in_transaction: True | видно в соединении: {'ACC-1': 100, 'ACC-2': 0}
после commit вызывающего: {'ACC-1': 100, 'ACC-2': 0}   ← полу-разнесённый файл зафиксирован
```

Транзакция остаётся открытой с половиной файла внутри. Спасает только то, что закрытие процесса откатит её — но любой обработчик, который поймает `KeyboardInterrupt` и корректно завершит работу через `commit()`, зафиксирует состояние, прямо запрещённое R3. Тест `test_broken_file_leaves_nothing_applied` проверяет только `ValueError` и этот путь не видит.

### R1 + Acceptance 1 — MAJOR, идемпотентность не по идентификатору платежа
`app/bank_import.py:67-70`

Поиск идёт по `state='active'`, то есть сравнение всегда с *последним* состоянием, а не с историей платежа. Повторная присылка исходной выгрузки после коррекции меняет остатки. Это буквально сценарий из постановки спеки («банк дважды за квартал присылал одну и ту же дневную выгрузку»):

```
day1 (100)        → ACC-1 = 100
fix  (130)        → ACC-1 = 130
ПОВТОР day1 (100) → ACC-1 = 100   ← «повторный запуск на том же файле» изменил остаток
ПОВТОР fix  (130) → ACC-1 = 130
```

Порядок файлов теперь определяет остаток, и каждая переприсылка плодит новую пару annulled/active. R1 выполняется только для тривиального случая «тот же файл дважды подряд» — который и покрыт тестом.

### Незакрытый «Открытый вопрос» спеки — MINOR (заметка)
`app/bank_import.py:63-64`

Спека явно фиксирует, что решение по неизвестному счёту (отбрасывать с отчётом vs блокировать файл) **не принято**. Дифф молча выбрал «блокировать весь файл» и закрепил выбор тестом, нигде его не отметив. Не дефект кода, но принятое за спеку проектное решение без следа.
