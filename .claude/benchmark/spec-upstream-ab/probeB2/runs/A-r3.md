## CRITICAL

### 1. `account_id` не участвует ни в сравнении, ни в пересчёте баланса → порча остатков
`app/bank_import.py:67-70`, `:83-84`, `:91-94`

Запрос `existing` выбирает только `id, amount` — счёт проводки игнорируется. Коррекция считается дельтой `amount - old_amount` и применяется к **новому** счёту, при этом старый счёт никогда не разгружается. Два режима отказа:

**A. Банк исправил номер счёта и сумму** — деньги размазываются между счетами:
```
1-й импорт:  P-1 / ACC-1 / 100   →  ACC-1=100, ACC-2=0
коррекция:   P-1 / ACC-2 / 130   →  ACC-1=100, ACC-2=30    (ожидалось 0 / 130)
```
Инвариант «баланс = сумма активных проводок» ломается по обоим счетам:
```
ACC-1  balance: 100   sum(active postings): 0     MISMATCH
ACC-2  balance: 30    sum(active postings): 130   MISMATCH
```

**B. Банк исправил только номер счёта** (`old_amount == amount`, строка 83) — коррекция **молча теряется**: `return False`, `applied = 0`, проводка остаётся висеть на `ACC-1`. Импорт при этом рапортует об успехе.

Корень: дельта-подход вместо «сторнировать старую проводку на её счёте + применить новую на её счёте». Нарушает R2 и AC1/AC2 по сути (коррекция не отражена корректно).

### 2. Аудит-след коррекции отсутствует — R2 `[hard]` и AC3 не выполнены
`app/bank_import.py:15-21` (схема), `:86` (аннулирование)

SPEC R2 требует «что было, что стало, **когда**», AC3 — «по любой аннулированной проводке увидеть, **когда** и **на что** её заменили». В `postings` нет ни одной колонки времени и нет ссылки на замену. Фактическое состояние после двух коррекций:

```
columns: ['id', 'payment_id', 'account_id', 'amount', 'state']
(1, 'P-3', 1, 100, 'annulled')
(2, 'P-3', 1, 130, 'annulled')
(3, 'P-3', 1, 150, 'active')
```

«Когда» — недоступно в принципе. «На что заменили» — только косвенно через порядок `id`, без явной связи; отличить «аннулирована и заменена» от «аннулирована и отменена» нельзя, как и понять, из какого файла пришла проводка. Отдельно важно: **это невосстановимо задним числом** — таймстемпы уже разнесённых коррекций не восстановить после факта. Ни один тест этого не проверяет.

## MAJOR

### 3. `BEGIN` + `rollback()` разрушают транзакцию вызывающего кода
`app/bank_import.py:41`, `:47-48`, `:27-28`

`sqlite3` работает с `isolation_level=''` (проверено: Python 3.12.3), т.е. неявные транзакции включены. Если у вызывающего есть незакоммиченная работа, `conn.execute("BEGIN")` падает, а `except Exception` вызывает `conn.rollback()` — **и стирает чужие данные**:

```
in_transaction before import: True
RAISED: OperationalError cannot start a transaction within a transaction
ACC-9 survived? (0,)        ← незакоммиченная строка вызывающего уничтожена
```

`import_file` управляет транзакцией соединения, которым не владеет. То же в `init_db:28` — безусловный `commit()` коммитит чужую работу. Правильнее: `isolation_level=None` + явное владение, либо savepoint, либо документированный контракт «передавайте чистое соединение».

### 4. Повторный импорт **старого** файла молча откатывает коррекцию
`app/bank_import.py:82-94`

AC1 («повторный запуск того же файла не меняет остатки») выполняется, но обратный сценарий не защищён — а он ровно из проблемы в SPEC («банк дважды за квартал присылал одну и ту же выгрузку»):

```
день 1 (100) → коррекция (130) → баланс 130
бухгалтер снова импортирует ИСХОДНЫЙ файл → баланс 100
```
Коррекция отменена, никакого предупреждения, `applied=1` как при нормальной работе. Нет ни происхождения проводки (файл/дата выгрузки), ни защиты от применения устаревших данных.

### 5. Схема не защищает инварианты, на которых держится вся логика
`app/bank_import.py:15-22`

- Нет частичного UNIQUE-индекса `ON postings(payment_id) WHERE state='active'` — ничто не мешает существованию двух активных проводок по одному платежу; тогда `fetchone()` (строка 70, без `ORDER BY`) выберет недетерминированную. R1 держится исключительно на коде.
- `state TEXT` без `CHECK (state IN ('active','annulled'))` — опечатка `'annuled'` сделает проводку невидимой одновременно для обоих запросов, без ошибки.
- `accounts.balance` денормализован, но сверка с `SUM(postings.amount) WHERE state='active'` не выполняется нигде — именно поэтому расхождение из находки №1 проходит незамеченным.
- Нет `FOREIGN KEY` enforcement: `REFERENCES` объявлен, но `PRAGMA foreign_keys=ON` не выставлен — в SQLite по умолчанию FK не проверяются.

### 6. Тесты дают ложную уверенность
`tests/test_bank_import.py`

3/3 зелёные, но: R2 (аудит-след) не проверяется вообще — только сумма активной проводки, не наличие следа; смена счёта в коррекции не покрыта (обе критические находки живут здесь); R4 не покрыт; инвариант «баланс = Σ активных проводок» не проверяется. Плюс `test_broken_file_leaves_nothing_applied:68-71` использует `try/except ValueError: pass` вместо `pytest.raises(ValueError)` — тест останется зелёным, даже если исключение перестанет подниматься вовсе.

### 7. Диагностика ошибок непригодна для целевого пользователя
`app/bank_import.py:57`

Поскольку по R3 падение блокирует **весь** файл, сообщение обязано указывать, какую строку чинить. Реально бухгалтер получает:
```
ValueError: invalid literal for int() with base 10: '1 200,50'
```
Ни номера строки, ни `payment_id`. Аналогично `row["payment_id"]` / `row["account"]` (строки 45, 56, 61) дадут голый `KeyError` при другом заголовке CSV, а `csv.DictReader` при недостающей колонке подставит `None` → `TypeError`. Валидации структуры файла нет.
