**Контекст:** реализация `init_db`/`import_file` поверх скелета, спека — `docs/SPEC.md` (R1–R5 hard/soft).

## CRITICAL

### 1. Коррекция со сменой счёта молча корёжит балансы двух счетов
`app/bank_import.py:67-70` (поиск существующей проводки), `:83-84`, `:91-94`

Поиск активной проводки идёт **только по `payment_id`**, счёт в сравнении не участвует. Дальше дельта `amount - old_amount` применяется к **новому** счёту, а старый счёт никто не разворачивает.

Подтверждено запуском, два проявления:

**(a) сменились и счёт, и сумма** — `P-1: ACC-1/100` → `P-1: ACC-2/130`:
```
actual  : ACC-1=100, ACC-2=30
expected: ACC-1=0,   ACC-2=130
postings: [(P-1, acc=1, 100, annulled), (P-1, acc=2, 130, active)]
```
На ACC-1 зависли 100 по аннулированной проводке, на ACC-2 вместо 130 попало 30. Сумма балансов не сходится с суммой активных проводок — деньги создаются/исчезают.

**(b) сменился только счёт, сумма та же** — `P-2: ACC-1/100` → `P-2: ACC-2/100`:
```
applied rows: 0
actual  : ACC-1=100, ACC-2=0
expected: ACC-1=0,   ACC-2=100
```
Ветка `old_amount == amount` → `return False`: коррекция отброшена целиком, проводка осталась на чужом счёте, импорт отчитался «0 применённых» без единой ошибки.

Оба случая — тихие, без исключения и без записи в лог. Это ровно тот класс, ради которого писалась спека (R2 — «изменение у уже разнесённого платежа = коррекция»); повторная выгрузка с исправленным счётом — сценарий не менее вероятный, чем с исправленной суммой. Ни один тест этого не трогает.

## MAJOR

### 2. R2/AC3 не выполнены: аудит-следа физически нет в схеме
`app/bank_import.py:15-21` (DDL), `:86`

AC3: *«бухгалтер может по любой аннулированной проводке увидеть, **когда** и **на что** её заменили»*. Фактические колонки `postings`:
```
['id', 'payment_id', 'account_id', 'amount', 'state']
```
Нет ни отметки времени, ни ссылки на заменяющую проводку. Аннулированная строка выглядит как `(1, 'P-3', 1, 100, 'annulled')` — из неё не выводится ни «когда», ни «на что». Если платёж корректировался дважды, цепочка замен восстанавливается только по неявному порядку `rowid` — то есть по совпадению, а не по данным.

R2 — hard-ограничение, и оно закрыто наполовину: аннулирование есть, аудит-след — нет. Тесты проверяют только `state='active'`, поэтому пробел невидим на зелёном прогоне.

### 3. Функция распоряжается чужим соединением: `BEGIN` падает и откатывает работу вызывающего
`app/bank_import.py:41`, `:47-48`

`import_file` получает `conn` снаружи, но безусловно делает `BEGIN` / `commit` / `rollback`. Если у вызывающего есть незакоммиченная работа:
```
in_transaction: True
RAISED: OperationalError - cannot start a transaction within a transaction
callers uncommitted row survived: []   # ← строка вызывающего уничтожена
```
`conn.execute("BEGIN")` падает, управление уходит в `except`, и `conn.rollback()` сносит **чужую** транзакцию. Импорт при этом не применён — то есть R3 формально соблюдён, но ценой разрушения постороннего состояния. Симметрично `conn.commit()` на строке 46 закоммитит всё, что вызывающий ещё не закончил.

Сейчас единственный вызывающий — CLI, поэтому не стреляет; это мина под любое будущее использование внутри более крупной транзакции.

### 4. Инвариант идемпотентности держится только на коде, БД его не защищает
`app/bank_import.py:15-22`, `:67-70`

- `PRAGMA foreign_keys` = `0` (sqlite по умолчанию), поэтому `REFERENCES accounts(id)` — декорация. Подтверждено: проводка с `account_id=9999` вставляется без возражений.
- Нет `UNIQUE`-ограничения «не более одной `active`-проводки на `payment_id`». Ключевой инвариант R1 живёт исключительно в `_apply_row`; любая другая запись (ручной фикс в проде, второй процесс импорта, будущий эндпоинт) ломает его молча.
- Как следствие, `fetchone()` на `:70` при нескольких активных проводках возьмёт произвольную — и дальше аннулирует/скорректирует не ту.
- Нет `CHECK (state IN ('active','annulled'))` — опечатка в состоянии превращает проводку в невидимую для обоих запросов.

## MINOR

### 5. Диагностика ошибок непригодна для пользователя-бухгалтера
`app/bank_import.py:57`, `:56`, `:64`

Реальные сообщения при кривом файле:
```
decimal amount        -> ValueError : invalid literal for int() with base 10: '100.50'
empty amount          -> ValueError : invalid literal for int() with base 10: ''
missing amount column -> KeyError   : 'amount'
```
Ни номера строки, ни имени колонки в человеческом виде. При R3 (весь файл блокируется) это означает: выгрузка на тысячи строк отвергнута целиком, а исправить нечего — непонятно, где ошибка. Пользователь по спеке — бухгалтер из CLI, а не разработчик.

Отдельно: `int(row["amount"])` фиксирует контракт «целое» (копейки?), но нигде это не записано — сумма `100.50` из банка валит импорт.

### 6. Утечка PII в логи закрыта, но остаётся один незакрытый путь
`app/bank_import.py:58`, `:45`, `:49`

R4 соблюдён по прямым путям: `phone` нигде не логируется и не печатается — это правильно сделано. Остаточный риск: весь `row` (включая телефон) лежит в локальных переменных фрейма `_apply_row`, а исключение пробрасывается наружу (`:50`). Любой сборщик наверху, который пишет локальные переменные фреймов — Sentry делает это по умолчанию (`include_local_variables=True`), — утащит телефон в лог. Дёшево закрывается тем, что `_apply_row` не держит весь `row`, а принимает уже извлечённые поля.

### 7. `print` в библиотечной функции, по строке на платёж
`app/bank_import.py:45`

R5 (soft) просит прогресс в консоли, но `print` внутри разносящей функции: нетестируемо, жёстко занимает stdout, не отключается. Подтверждено — 2000 строк вывода на 2000 платежей. Плюс строки печатаются **до** `commit`: при откате пользователь видит «прогресс» по строкам, которые в итоге не применены. Место такому выводу — в CLI-слое (callback/`logging`), с шагом, а не на каждую строку.

### 8. `log.error` без стека
`app/bank_import.py:49`

`log.error("import failed, file not applied: %s", path)` без `exc_info=True`: в логе остаётся факт падения без причины. Причина есть только в проброшенном исключении — если наверху его залогируют.

### 9. Открытый вопрос спеки решён молча
`app/bank_import.py:63-64`

`docs/SPEC.md:26-27` явно фиксирует нерешённое: строки с неизвестным счётом — отбрасывать с отчётом или блокировать файл. Код выбрал «блокировать весь файл», и `tests/test_bank_import.py:63` этот выбор закрепил. Решение продуктовое: одна опечатка в номере счёта отменяет разноску всей дневной выгрузки. Это стоит проговорить с заказчиком, а не утвердить по умолчанию через дифф.

### 10. Семантика возвращаемого `applied` двусмысленна
`app/bank_import.py:39-44`, `:84`

Считаются только строки, изменившие состояние. Повторный импорт того же файла (штатный сценарий R1, ради которого всё писалось) вернёт `0` при полностью корректной работе. Для бухгалтера `0` читается как «ничего не сделано / что-то сломалось». Либо переименовать, либо возвращать пару (обработано / изменено).

### 11. Артефакты в рабочем дереве
`err.log`, `out.md` — пустые файлы в корне, не в `.gitignore`, рискуют уехать в коммит.

*Отдельно, не из этого диффа и не трогал:* `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` уже закоммичены в `HEAD` (`0208317`).

## Покрытие тестами

Три теста зелёные и покрывают R1, R2 (по сумме) и R3. Не покрыто ничего из того, где лежат находки 1–4:
- коррекция со сменой счёта (находка 1, оба варианта);
- содержимое аннулированной проводки — «когда» и «на что заменили» (находка 2);
- повторный импорт **после** коррекции;
- инварианты БД: две активные проводки на один `payment_id`, проводка на несуществующий счёт (находка 4);
- сверка «сумма балансов == сумма активных проводок» — этот инвариант поймал бы находку 1 автоматически на любом сценарии.
