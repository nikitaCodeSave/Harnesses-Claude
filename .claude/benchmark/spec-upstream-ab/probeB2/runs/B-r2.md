# Ревью диффа `app/bank_import.py`

**Базовый факт:** все 3 теста в `tests/test_bank_import.py` проходят. Ни одна находка ниже не ловится существующим набором тестов — все проверены отдельными запусками.

---

## Ось 1 — Standards

### S1 · CRITICAL · `app/bank_import.py:91-94` — коррекция со сменой счёта портит баланс обоих счетов

При коррекции баланс правится дельтой `amount - old_amount`, но применяется к **новому** `account_id`. Если платёж пришёл повторно с другим счётом, старый счёт никто не разгружает.

```
P-1 = 100 на ACC-1  →  {ACC-1: 100, ACC-2: 0}
P-1 = 130 на ACC-2  →  {ACC-1: 100, ACC-2: 30}    ожидалось {ACC-1: 0, ACC-2: 130}
```

Оба остатка неверны. Общая сумма сходится (130), поэтому сверка «итого» дефект не поймает — он виден только по конкретному клиенту. Это тот же класс ущерба, из-за которого спека вообще написана.

### S2 · MAJOR · `app/bank_import.py:47` — `except Exception` не ловит `KeyboardInterrupt`

Пользователь по спеке — бухгалтер, запускающий импорт **руками из CLI**. Ctrl+C в середине файла → `BaseException` проходит мимо `except`, `conn.rollback()` не вызывается, транзакция остаётся открытой с уже применёнными строками. Проверено: после прерывания на 2-й строке `in_transaction=True`, ACC-1 уже 100, и любой последующий `commit()` на этом соединении фиксирует полу-разнесённый файл.

### S3 · MAJOR · `app/bank_import.py:41,48` — явный `BEGIN` + безусловный `rollback()` разрушают чужую транзакцию

`conn.execute("BEGIN")` падает с `OperationalError: cannot start a transaction within a transaction`, если на соединении уже есть незакоммиченная работа вызывающего. Обработчик `except` тогда делает `conn.rollback()` — и **стирает чужие незакоммиченные изменения**, к которым импорт отношения не имеет:

```
до import_file:  ACC-1 = 999 (uncommitted)
после:           ACC-1 = 0     ← откачено импортом
```

Функция откатывает то, чего не начинала. Правильно — либо `with conn:`, либо откат только собственной транзакции (savepoint).

### S4 · MAJOR · `app/bank_import.py:15-22` — инвариант «одна активная проводка на платёж» не защищён схемой

Вся корректность строится на допущении, что `SELECT ... WHERE payment_id = ? AND state = 'active'` вернёт максимум одну строку, но `fetchone()` молча берёт первую попавшуюся. БД принимает две active-проводки на один `payment_id` без возражений (проверено). Нет partial unique index `ON postings(payment_id) WHERE state='active'`, нет `CHECK (state IN ('active','annulled'))`. Единственная защита — код, который сам же может её нарушить при частичном сбое.

### S5 · MINOR · `app/bank_import.py:18` — внешний ключ декоративен

`REFERENCES accounts(id)` без `PRAGMA foreign_keys = ON` в SQLite не применяется вообще (проверено: `PRAGMA foreign_keys = 0`). Читается как гарантия, гарантией не является.

### S6 · MINOR · `app/bank_import.py:45` — `print()` в библиотечной функции внутри транзакции

Прогресс идёт в stdout, диагностика — в `logging`; два несинхронных канала. Вывод неотключаем (нет флага, нет проверки tty), пишется на каждую строку внутри открытой транзакции, удлиняя удержание блокировки БД. Библиотечному коду не место решать за вызывающего, куда писать.

### S7 · MINOR · `app/bank_import.py:56-57` — нет валидации входных данных, ошибки без координат

`int(row["amount"])` роняет весь файл на `'100.50'`, `''`, `'1 000'` — с сообщением `invalid literal for int()`, где нет ни номера строки, ни `payment_id`. Отсутствующая колонка → голый `KeyError: 'amount'`. Бухгалтер по такому сообщению не поймёт, что чинить. Заголовок CSV не валидируется вовсе; единица измерения `amount` (рубли? копейки?) нигде не зафиксирована, хотя схема `INTEGER`.

### S8 · MINOR · возврат `applied` вводит в заблуждение

Docstring обещает «число применённых строк», но фактически считаются только строки, **изменившие состояние**. Повторный импорт корректно разнесённого файла вернёт `0` — что для оператора неотличимо от «файл не разнёсся».

### Замечено, не трогал (вне диффа)
`__pycache__/*.pyc` отслеживаются в git и меняются от диффа; `err.log` и `out.md` (оба пустые) лежат неотслеживаемыми. `.gitignore` в репозитории отсутствует.

## Ось 2 — Spec-faithfulness (оракул `docs/SPEC.md`)

### R2 `[hard]` + AC#3 · MAJOR · НЕ ВЫПОЛНЕНО — `app/bank_import.py:15-21`

> «коррекция с аудит-следом (что было, что стало, **когда**)» / «увидеть, **когда** и **на что** её заменили»

Схема `postings` — `id, payment_id, account_id, amount, state`. Нет **ни одной** отметки времени и нет ссылки `replaced_by`. Реально доступно после коррекции:

```
(1, 'P-1', 1, 100, 'annulled')
(2, 'P-1', 1, 130, 'active')
```

«Что было / что стало» бухгалтер восстановит только косвенно — упорядочив по `id` и догадавшись, что это цепочка. «Когда» — не восстановимо никак, ни задним числом. «На что заменили» явной ссылки не имеет. Требование помечено `[hard]`, реализовано частично и неявно.

### R1 `[hard]` + AC#1 · MAJOR · НАРУШАЕТСЯ НА РЕАЛЬНОМ ПУТИ — `app/bank_import.py:83-94`

> «Повторный запуск на том же файле не меняет остатки по счетам»

Выполняется только пока не было коррекции. Ровно в сценарии из преамбулы спеки — банк присылает ту же дневную выгрузку второй раз за квартал — если между присылками бухгалтер применил коррекцию, повторный импорт **исходного** файла её молча откатывает:

```
1) day1.csv (100)        → ACC-1 = 100
2) day1-fix.csv (130)    → ACC-1 = 130   коррекция
3) day1.csv ещё раз      → ACC-1 = 100   ← коррекция отменена
```

Логика last-write-wins не отличает «новую информацию» от «старого дубля». Тест `test_repeated_file_does_not_double_charge` этот путь не покрывает — он не комбинирует коррекцию с повторной присылкой.

### R1 `[hard]` · MAJOR · НЕ ВЫПОЛНЕНО — `app/bank_import.py:83-84`

Идемпотентность объявлена «по идентификатору платежа», но сравнивается только `amount`. Если тот же `payment_id` пришёл с тем же `amount`, но **другим счётом** — `return False`, изменение отбрасывается без записи, без лога, без ошибки. Платёж остаётся на неверном счёте, и никто об этом не узнаёт. См. также S1 — вторая половина той же дыры: когда счёт меняется вместе с суммой, деньги размазываются по двум счетам.

### R3 `[hard]` · MAJOR · НАРУШАЕТСЯ НА РЕАЛЬНОМ ПУТИ

> «Частично разнесённый файл недопустим»

Заявлено в docstring («при любой ошибке транзакция откатывается»), выполняется для `Exception`, но ломается на Ctrl+C — см. S2. Для CLI-инструмента, который человек запускает руками, прерывание с клавиатуры это не экзотика, а штатный способ остановки. Побочный эффект из S3 — нарушение той же атомарности с обратной стороны.

### R4 `[hard]` · ВЫПОЛНЕНО

Проверено захватом root-логгера на уровне DEBUG по путям успеха и ошибки: телефон не попадает ни в `log.info`, ни в `log.error`, ни в текст `ValueError`, ни в `print`. Замечание без severity: гарантия держится на том, что автор перечислил поля вручную — нет ни явного whitelist полей, ни фильтра в логгере, ни теста, который бы зафиксировал требование. Первый же `log.debug("row=%s", row)` его нарушит незаметно.

### R5 `[soft]` · ВЫПОЛНЕНО

Прогресс `[idx/total] payment_id` виден. Претензии к реализации — в S6, по сути требования вопросов нет.

### Открытый вопрос спеки решён молча · MINOR

> «Строки со счётом, которого нет в биллинге: отбрасывать с отчётом или блокировать весь файл — решение не принято.»

Дифф выбрал «блокировать весь файл» (`raise ValueError`, строка 64) и закрепил выбор тестом `test_broken_file_leaves_nothing_applied`. Выбор может быть верным, но он нигде не зафиксирован как принятое решение — ни в `SPEC.md`, ни в комментарии. Отчёта по проблемным строкам тоже нет: бухгалтер получает исключение по **первой** встреченной, о ещё пяти таких же в файле узнает только на следующей итерации.
