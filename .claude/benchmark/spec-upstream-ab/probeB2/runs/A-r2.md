# Ревью `app/bank_import.py` (незакоммиченный дифф)

## CRITICAL

### 1. Коррекция со сменой счёта разносит дельту на новый счёт, старый не сторнируется
`app/bank_import.py:82-94`

`existing` ищется **только по `payment_id`**, без учёта счёта, а `account_id` берётся из новой строки. Далее баланс правится как `+ (amount - old_amount)` на **новом** счету, тогда как старый счёт остаётся с прежней суммой.

Проверено: платёж `P-1` пришёл на `ACC-1` = 100, затем банк исправил на `ACC-2` = 130.
```
balances: {'ACC-1': 100, 'ACC-2': 30}   ожидалось {'ACC-1': 0, 'ACC-2': 130}
```
Общая сумма сходится случайно, распределение по счетам — нет. Клиент `ACC-1` списан за платёж, которого у него не было. Нарушает R2/AC2.

### 2. Смена счёта при неизменившейся сумме молча игнорируется
`app/bank_import.py:83-84`

`if old_amount == amount: return False` — счёт не сравнивается вовсе. Коррекция «тот же платёж, другой счёт» полностью теряется, `applied` = 0, ни лога, ни ошибки.
```
P-1: ACC-1/100 → ACC-2/100  ⇒ balances: {'ACC-1': 100, 'ACC-2': 0}
postings: [(1, 'P-1', account_id=1, 100, 'active')]   # проводка не тронута
```
Это молчаливая потеря коррекции — худший класс дефекта: не видно ни в логах, ни в возвращаемом значении.

### 3. Аудит-след аннулирования отсутствует — R2/AC3 (hard) не выполнено
`app/bank_import.py:15-23` (SCHEMA), `86`

`postings` содержит только `id, payment_id, account_id, amount, state`. Нет ни времени аннулирования, ни ссылки «заменена проводкой N». Требование AC3 — «бухгалтер может по любой аннулированной проводке увидеть, **когда и на что** её заменили» — не закрыто ничем:
```
columns: ['id', 'payment_id', 'account_id', 'amount', 'state']
rows: [(1,'P-1',1,100,'annulled'), (2,'P-1',1,130,'active')]
```
Связь восстанавливается только эвристикой «следующий по rowid с тем же payment_id», времени нет вообще. При двух и более коррекциях подряд история нечитаема. Блокер приёмки по hard-ограничению R2.

## MAJOR

### 4. Функция управляет транзакцией на чужом соединении и откатывает чужую работу
`app/bank_import.py:41, 47-50`

`conn.execute("BEGIN")` падает, если вызывающий уже открыл транзакцию, а `except`-ветка вызывает `conn.rollback()` — то есть **уничтожает незакоммиченные изменения вызывающего**, к импорту отношения не имеющие. Проверено:
```
FAIL OperationalError cannot start a transaction within a transaction
ACC-9 (незакоммиченная строка вызывающего) после вызова: []   # затёрта
```
Правильная форма для вложенности — `SAVEPOINT`, либо явный контракт «соединение принадлежит функции». Сейчас R3 держится только на том, что вызывающий соблюдает необъявленное правило.

### 5. Инвариант идемпотентности (R1, hard) не выражен в схеме
`app/bank_import.py:15-23, 67-70`

Индекс `postings_payment` — **не** UNIQUE, CHECK на «≤1 активной проводки на payment_id» нет. `fetchone()` молча берёт первую из нескольких активных. Если дубль возникнет (параллельный запуск, ручная правка, будущая миграция на СУБД с MVCC), расхождение не обнаружится:
```
до реимпорта: balance=200, активных проводок=2
после коррекции до 130: balance=230, sum(active)=230   # осталось 2 активных: 100 и 130
```
R1 обеспечен только паттерном read-then-write в приложении — на SQLite спасает блокировка записи, но защиты уровня данных нет.

### 6. `int(row["amount"])` не переживает реальную банковскую выгрузку
`app/bank_import.py:57`

```
"100.50" → ValueError: invalid literal for int() with base 10: '100.50'
""       → ValueError
```
Любая такая строка откатывает **весь файл**. Дневная выгрузка платежей почти всегда содержит копейки. Плюс единица измерения (`INTEGER` — рубли или копейки?) нигде не задокументирована ни в схеме, ни в докстринге, ни в SPEC — это молчаливое допущение о деньгах.

### 7. Нет валидации формата файла; ошибки нечитаемы для бухгалтера
`app/bank_import.py:36-37, 45, 56, 61`

Отсутствующая колонка даёт `KeyError: 'amount'` — без имени файла, без номера строки, без подсказки. Заголовок CSV не проверяется перед началом транзакции. Пользователь по спеке — бухгалтер за CLI, для него это тупик.

### 8. Открытый вопрос спеки закрыт молча
`app/bank_import.py:63-64`

SPEC, раздел «Открытое»: «Строки со счётом, которого нет в биллинге: отбрасывать с отчётом или блокировать весь файл — **решение не принято**». Код выбрал «блокировать весь файл» (`raise ValueError`) и зафиксировал это тестом `test_broken_file_leaves_nothing_applied`. Нерешённое продуктовое решение принято реализацией без пометки и без флага — при пересмотре придётся менять и код, и тест.

## Покрытие тестами

Три существующих теста зелёные, но ни один не проверяет:
- AC3 (аудит-след) — дефект №3 проходит незамеченным;
- смену счёта у платежа — дефекты №1 и №2;
- R4 (PD в логах) — вообще не проверяется, хотя это hard-ограничение;
- суммы с копейками и битый заголовок.

Тесты закрепляют ровно те три сценария, что реализованы, — классический случай, когда зелень маскирует невыполненные hard-требования.
