# Ревью диффа `app/bank_import.py`

## Ось 1 — Standards

### 1. `[critical]` Коррекция со сменой счёта не откатывает старый счёт — деньги искажаются
`app/bank_import.py:67-70` и `:91-94`

Поиск существующей проводки идёт **только по `payment_id`**, без учёта счёта, а обратная дельта `amount - old_amount` применяется к **новому** `account_id`. Если банк исправил у платежа не только сумму, но и счёт, старая проводка помечается `annulled`, но баланс её счёта не откатывается вообще.

Репро (P-1: `ACC-1/100` → `ACC-2/130`):
```
после первого импорта:  {'ACC-1': 100, 'ACC-2': 0}
после коррекции:        {'ACC-1': 100, 'ACC-2': 30}   # ожидалось ACC-1: 0, ACC-2: 130
```
На ACC-1 висит списание по аннулированной проводке, на ACC-2 недостача 100. Сумма балансов (130) случайно совпала с корректной, поэтому агрегатная сверка это не поймает.

### 2. `[critical]` Ранний `return False` пропускает коррекцию счёта при неизменной сумме
`app/bank_import.py:83-84`

`if old_amount == amount: return False` — единственный критерий «ничего не изменилось». Если банк исправил только счёт, строка молча считается идемпотентным повтором.

Репро (P-9: `ACC-1/100` → `ACC-2/100`):
```
балансы: {'ACC-1': 100, 'ACC-2': 0}
проводки: [(1, 'P-9', account_id=1, 100, 'active')]   # коррекция не применена вовсе
```
Общий корень с находкой 1: «тождество проводки» в коде = `payment_id`, а «состояние» = только `amount`; счёт выпал из обеих ролей.

### 3. `[major]` `import_file` захватывает и откатывает транзакцию вызывающего
`app/bank_import.py:41`, `:48`

Функция безусловно делает `conn.execute("BEGIN")` и `conn.rollback()` на переданном соединении. Если у вызывающего уже открыта транзакция, `BEGIN` падает, и `except` откатывает **чужую** незакоммиченную работу:
```
до import_file: ACC-NEW есть? 1
import_file упал: OperationalError cannot start a transaction within a transaction
после import_file: ACC-NEW есть? 0    # откачено чужое
```
Побочно: `BEGIN` здесь DEFERRED — блокировка на запись берётся не в начале, а на первом DML.

### 4. `[minor]` `log.error` без `exc_info` — причина сбоя не попадает в лог
`app/bank_import.py:49`

В логе останется только «import failed, file not applied: <path>». Исходное исключение уходит наружу через `raise`, и если верхний уровень его не залогирует, диагностика для бухгалтера потеряна.

### 5. `[minor]` `print()` из библиотечной функции, прогресс печатается до `commit`
`app/bank_import.py:45`

Вывод неотключаем, идёт в stdout (мешает пайпам и тестам), и главное — при откате пользователь уже увидел `[1/5] … [3/5]` без последующей пометки «файл не применён».

### 6. `[minor]` Разбор строки без валидации: непонятная ошибка на весь файл
`app/bank_import.py:56-57`

`int(row["amount"])` на `"100.50"` даёт `ValueError: invalid literal for int() with base 10: '100.50'` — без номера строки и `payment_id`; отсутствие колонки даёт голый `KeyError`. При этом схема хранит `amount INTEGER`, а формат сумм (копейки/рубли) нигде не зафиксирован.

### 7. `[minor]` Идемпотентность держится только на прикладном read-then-write
`app/bank_import.py:15-22`

В схеме нет уникального индекса на активную проводку (`CREATE UNIQUE INDEX … ON postings(payment_id) WHERE state='active'`). R1 — hard-требование, а гарантия его — только последовательность SELECT→INSERT без блокировки. Механический констрейнт был бы дешёвой страховкой; заодно ловил бы находки 1-2 на уровне БД.

### 8. `[minor]` Возвращаемое значение расходится с docstring
`app/bank_import.py:32`, `:44`

Обещано «число применённых строк», фактически считаются строки, **изменившие состояние**: повторный импорт того же файла возвращает `0`, хотя все строки применены.

### 9. `[minor]` Гигиена рабочего дерева
Пустые `err.log` и `out.md` не отслеживаются и не в `.gitignore`; в индексе лежат `app/__pycache__/*.pyc` и `tests/__pycache__/*.pyc` (они меняются от диффа). `.gitignore` в репозитории отсутствует.

## Ось 2 — Spec-faithfulness (оракул `docs/SPEC.md`)

| Требование | Статус |
|---|---|
| R1 идемпотентность | нарушено на пути смены счёта |
| R2 коррекция с аудит-следом | не выполнено в части аудит-следа |
| R3 атомарность файла | нарушено на пути прерывания |
| R4 ПДн не в логах | выполнено |
| R5 прогресс в консоли | выполнено |

### S1. `[major]` R2 / AC#3 — аудит-след не пишется: нет «когда» и нет «на что заменили»
`app/bank_import.py:15-21` (схема `postings`), `:86`

R2 требует «что было, что стало, **когда**», AC#3 — «по **любой** аннулированной проводке увидеть, **когда** и **на что** её заменили». В таблице есть только `id, payment_id, account_id, amount, state`; аннулирование — просто `state='annulled'`. Нет ни временной метки, ни ссылки `replaced_by`.

Репро (P-5: 100 → 130 → 170):
```
колонки postings: ['id', 'payment_id', 'account_id', 'amount', 'state']
проводки P-5: [(1,'P-5',100,'annulled'), (2,'P-5',130,'annulled'), (3,'P-5',170,'active')]
```
По проводке `id=1` бухгалтер не может ответить ни на «когда», ни на «на что заменили» — двух annulled-проводок достаточно, чтобы цепочка стала неоднозначной. Требование выглядит выполненным (`annulled` есть, тест зелёный), но данные для ответа не сохраняются и восстановить их задним числом невозможно.

### S2. `[major]` R3 / AC#4 — прерывание в середине файла оставляет полу-разнесённое состояние
`app/bank_import.py:47`

`except Exception` не покрывает `BaseException`; `finally`/context-manager нет. При Ctrl+C (а бухгалтер по спеке запускает импорт **руками из CLI** — это самый вероятный «сбой в середине файла») откат не выполняется и транзакция остаётся открытой на соединении:
```
!! Ctrl+C: бухгалтер нажал Ctrl+C
in_transaction после прерывания: True
после последующего commit(): {'ACC-1': 300}
проводок в БД: 3 из 5          # файл разнесён частично
```
Достаточно, чтобы верхний уровень поймал `KeyboardInterrupt` и продолжил работать с тем же соединением — любой следующий `commit()` зафиксирует половину файла. Существующий тест проверяет только `ValueError`, поэтому дыру не видит.

### S3. `[critical]` R1 / AC#2 — коррекция реализована неверно на пути смены счёта
См. Standards 1 и 2. По спеке: AC#2 («прежняя проводка аннулирована, действует новая») не выполняется — при неизменной сумме коррекция не применяется вовсе, при изменившейся сумме остатки обоих счетов оказываются неверны. R1 (идемпотентность по идентификатору платежа) де-факто реализован как идемпотентность по паре (payment_id, amount) с игнорированием счёта.

### S4. `[minor]` R4 выполнен, но ничем не закреплён
`app/bank_import.py:45`, `:58`, `:64`

Проверил все точки вывода: `print` — только `payment_id`, `log.info` — `payment_id` и сумма, `log.error` — путь файла, текст `ValueError` — `payment_id`. Телефон не логируется и не пишется в БД, требование выполнено. Но словарь `row` целиком (вместе с `phone`) передаётся в `_apply_row`, теста на R4 нет — hard-требование держится на дисциплине, а не на структуре.

### S5. `[minor]` Открытый вопрос спеки закрыт молча
`app/bank_import.py:63-64`

Спека прямо фиксирует: «Строки со счётом, которого нет в биллинге: отбрасывать с отчётом или блокировать весь файл — **решение не принято**». Дифф принял вариант «блокировать весь файл» (`raise ValueError`), причём без отчёта бухгалтеру о проблемной строке — в лог уходит только «import failed». Тест `test_broken_file_leaves_nothing_applied` этот выбор закрепляет. Само решение защитимо, но оно не согласовано и нигде не помечено как принятое.

## Итог

Реализация проходит все три существующих теста и при этом ломает деньги на первом же реалистичном сценарии за их пределами (банк исправил счёт), не даёт аудит-следа, которого требует hard-требование R2, и теряет атомарность при Ctrl+C. Блокирующие к мержу: **S3 / Standards 1-2** (порча балансов), **S2** (R3), **S1** (R2/AC#3). Находка Standards 3 — следующая по приоритету.
