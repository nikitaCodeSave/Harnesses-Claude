# Импорт банковской выгрузки в биллинг — PRD-lite

## Проблема

Ежедневная выгрузка платежей от банка (CSV на S3) разносится по счетам клиентов **вручную бухгалтером**. Дважды за квартал банк присылал один и тот же файл повторно — бухгалтер разносил его второй раз, клиент получал двойное списание. В первом случае это обнаружили только по жалобе клиента.

Главная боль: **повторная выгрузка не должна приводить к повторному списанию**. Цена ошибки — деньги клиента и разбирательство с ним постфактум. Вторичная боль: ручная разноска дорогая и медленная сама по себе.

## Пользователь

Бухгалтер. Сценарий: увидел, что файл появился на S3 → запускает импорт руками из CLI → получает результат разноски и понятный отчёт о том, что произошло. При запросе аудитора должен уметь объяснить любую проводку и любое аннулирование.

## Success (done)

1. **Идемпотентность по платежу.** Импорт файла, все платежи которого уже разнесены, не меняет сальдо ни одного счёта и не создаёт ни одной новой проводки; CLI сообщает, сколько строк пропущено как уже импортированные. Критерий проверяется повторным запуском на том же файле и запуском на файле, где часть платежей новая, а часть — уже разнесённая.
2. **Коррекция вместо дубля.** Если приходит запись с уже известным идентификатором платежа, но другой суммой — прежняя проводка переводится в состояние «аннулирована» (не удаляется), создаётся новая на новую сумму. Итоговое влияние на счёт равно новой сумме, а не сумме обеих.
3. **Аудит-след.** По идентификатору платежа доступна запись: кто и когда аннулировал, сумма до, сумма после, из какого файла пришла коррекция. Достаточна, чтобы бухгалтер объяснил аудитору историю проводки без чтения логов и кода.
4. **Атомарность файла.** При ошибке на произвольной строке N (битая строка, отказ БД) после завершения команды в биллинге нет **ни одной** проводки из этого файла; команда завершается ненулевым кодом и указывает номер проблемной строки. Частичное состояние недостижимо.
5. **PII не течёт в логи.** После прогона файла с телефонами клиентов поиск любого из этих телефонов по всем логам процесса (включая уровень DEBUG, тексты ошибок парсинга и stacktrace) даёт ноль совпадений.

## Ограничения

- Формат один: CSV конкретного банка, приходит раз в сутки на S3. Файл содержит телефон клиента — PII, был инцидент с утечкой PII в логи, повтор недопустим.
- Файл не гигантский — чтение целиком в память приемлемо (pandas допустим, но не обязателен).
- Аннулирование только логическое: физическое удаление или правка проводок «на месте» запрещены — они ломают критерий 3.
- Точка входа — CLI, ручной запуск. Автоматизации запуска нет.
- Размещение: `app/services/bank_import.py`, рядом с остальными интеграциями.
- Существующий API биллинга не изменяется.
- Предложение оператора (**не обязательство**): таблица `imported_rows` с уникальным индексом по `(file_hash, row_no)`. Отмечено им же как «детали». См. первый пункт «Открытого» — этот ключ решает не ту задачу, что критерий 1.

## NON-GOALS

- Автозапуск по событию из S3 — в первой версии только руками.
- Поддержка других банков и других форматов выгрузки.
- Любые изменения существующего API биллинга.
- Прогресс в консоли — оператор явно назвал это приятной мелочью, не критично; в критерии done не входит.
- Замена бухгалтера как контролирующего звена: он по-прежнему решает, когда запускать и что делать с отчётом.

## Открытое

1. **Строки без найденного счёта клиента** — отбрасывать с отчётом или блокировать весь файл. Решение за оператором; от исполнителя требуется предложить варианты **с обоснованием**, а не выбрать молча.
2. **Ключ дедупликации** (не поднималось в сессии, но следует из требований). Критерий 1 сформулирован по идентификатору платежа, а предложенный `(file_hash, row_no)` защищает только от повторного импорта побайтово того же файла. Если банк пришлёт те же платежи в файле с другим хешем (переупорядоченные строки, лишняя колонка, файл-коррекция), дедупликация по хешу не сработает, а по `payment_id` — сработает. Развилку нужно закрыть до реализации: это прямо про главную боль.
3. **Коррекция платежа из закрытого периода** (не поднималось в сессии). Что делать, если коррекция приходит на проводку прошлого отчётного периода — аннулировать задним числом или заводить компенсирующую проводку текущей датой. Влияет на форму аудит-следа.
