# Спека: импорт банковской выгрузки в биллинг

## Проблема

Ежедневную выгрузку платежей от банка (CSV на S3) бухгалтер разносит по счетам клиентов вручную. Дважды за квартал банк присылал один и тот же файл повторно, и повторная разноска приводила к двойному списанию у клиента — в первый раз это заметили только по жалобе клиента. Цена ошибки — деньги клиента и объяснение перед аудитором. Ручной труд вторичен: главная боль — отсутствие защиты от повторной обработки.

## Пользователь

Бухгалтер. Видит, что файл появился на S3, и запускает импорт руками из CLI. Ему нужно понимать, что импорт либо полностью прошёл, либо полностью не прошёл, и уметь показать аудитору историю изменений по конкретной проводке.

## Success (done) — acceptance criteria

1. **Идемпотентность по файлу.** Повторный запуск импорта на том же файле (тот же `file_hash`) не создаёт ни одной новой проводки и не меняет балансы счетов; итоговое состояние биллинга совпадает с состоянием после первого запуска. CLI сообщает, что файл уже импортирован.
2. **Коррекция по идентификатору платежа.** Запись с уже известным `payment_id`, но другой суммой не создаёт вторую проводку: прежняя проводка помечается аннулированной, вместо неё встаёт новая с новой суммой. Баланс счёта отражает только новую сумму.
3. **Аудит-след коррекции.** По аннулированной проводке можно получить: кто и когда аннулировал, прежнюю сумму, новую сумму, ссылку на исходную запись (файл + номер строки). Записи не удаляются и не перезаписываются.
4. **Атомарность.** Если импорт прерывается на любой строке (ошибка данных, падение процесса), в биллинге не остаётся ни одной проводки из этого файла — повторный запуск начинает с чистого состояния. Проверяется тестом с искусственным падением в середине файла.
5. **Ноль PII в логах.** Ни на одном уровне логирования (включая DEBUG и трейсбеки исключений) телефон клиента не попадает в вывод. Проверяется тестом: прогон файла с известным телефоном → grep по всему логу не находит его.

## Ограничения

- Формат входа фиксирован: один CSV от одного банка, забирается с S3.
- Место в коде: `app/services/bank_import.py`, рядом с остальными интеграциями.
- Чтение файла — pandas (файл не гигантский, размер не является ограничением).
- Запуск — CLI, вручную.
- Существующий API биллинга не меняется.
- Идентичность файла определяется его хешем; идентичность платежа — `payment_id` из выгрузки. Дедупликация строк предполагается через таблицу `imported_rows` с уникальным индексом по `(file_hash, row_no)` — это ориентир, а не жёсткое требование к схеме.

## NON-GOALS

- Автозапуск по событию из S3 — в первой версии только ручной CLI.
- Поддержка форматов других банков.
- Изменения в существующем API биллинга.
- Прогресс-бар в консоли — желателен, но явно необязателен; отсутствие не блокирует приёмку.

## Открытое

- **Строки со счётом, не найденным в биллинге.** Не решено: отбрасывать такие строки с отчётом в конце или блокировать импорт всего файла. Оператор явно просил: предложить варианты с обоснованием и дать ему выбрать, а не решать молча. Решение нужно до реализации — оно меняет критерий №4 (что считать «файл разнесён целиком»).
