# Импорт банковской выгрузки платежей в биллинг — PRD-lite

## Проблема

Ежедневную выгрузку платежей от банка бухгалтер разносит по счетам клиентов вручную. Дважды за квартал банк присылал один и тот же файл повторно; в первый раз повторное списание обнаружили только по жалобе клиента. Цена ошибки — деньги клиента и объяснение с аудитором. Ручной процесс не даёт ни защиты от повтора, ни следа, по которому можно восстановить, что и почему изменилось.

## Пользователь

Бухгалтер. Видит, что файл появился, и запускает разнесение руками из CLI. Ему нужно понимать, чем закончился запуск, и уметь объяснить аудитору любую проводку.

## Success (done)

1. **Повтор не двоит деньги.** Повторный запуск на уже разнесённой выгрузке не изменяет балансы счетов и не создаёт новых проводок; результат запуска сообщает, что разнесено 0 новых записей.
2. **Коррекция видна как коррекция.** Для записи с уже известным идентификатором платежа, но другой суммой: прежняя проводка аннулирована, действует новая, а в аудит-следе доступны прежняя сумма, новая сумма, автор и время аннулирования. Итоговый баланс счёта соответствует только новой сумме.
3. **Нет полуразнесённых файлов.** Если запуск прерван на любой строке (ошибка данных, падение процесса), состояние биллинга после него неотличимо от состояния до запуска — ни одной проводки из этого файла.
4. **PII не утекает.** Телефон клиента не встречается ни в одной строке логов при любом исходе запуска, включая ошибки и трассировки стека.
5. **Запуск заканчивается отчётом.** По завершении бухгалтер получает сводку: сколько записей разнесено, сколько распознано как коррекции, сколько не разнесено и по какой причине — без необходимости лезть в базу.

## Ограничения

- `[hard]` Операция идемпотентна по содержимому выгрузки: повторная обработка тех же платежей не меняет финансовое состояние.
- `[hard]` Импорт файла атомарен: применяется целиком либо не применяется вовсе. Частичное применение недопустимо даже ценой отказа от импорта.
- `[hard]` Повтор идентификатора платежа с изменённой суммой трактуется как коррекция ранее проведённого платежа, а не как новый платёж.
- `[hard]` Аудит-след коррекций неразрушающий: прежнее значение не затирается, история пригодна для предъявления аудитору.
- `[hard]` PII из выгрузки (как минимум телефон) не попадает в логи ни на одном уровне логирования и ни в одной ветке обработки ошибок.
- `[hard]` Существующий публичный API биллинга не изменяется.
- `[soft]` Индикация прогресса в консоли, чтобы бухгалтер видел, что процесс живой. Можно пожертвовать ради простоты.

## NON-GOALS

- Автозапуск по событию появления файла — в первой версии запуск только ручной.
- Поддержка выгрузок других банков и других форматов — формат ровно один.
- Любые изменения существующего API биллинга.
- UI поверх импорта — интерфейс запуска только консольный.
- Автоматическое «исправление» проблемных строк (подбор счёта, догадки по клиенту).

## Открытое

- **Строки с ненайденным в биллинге счётом.** Два варианта: отбросить их и вывести в отчёт (файл проходит) либо считать это отказом всего файла. Решение за оператором — исполнитель обязан вынести оба варианта с обоснованием (риск тихой потери платежа против риска блокировки всей выгрузки), а не выбрать молча.
- **Границы понятия «тот же платёж».** Идентификатор платежа от банка принят за ключ; не решено, что делать, если банк меняет не сумму, а другие поля записи (счёт, дату) при том же идентификаторе.
- **Срок и глубина хранения аудит-следа** не обсуждались.
