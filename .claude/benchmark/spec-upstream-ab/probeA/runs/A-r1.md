# Импорт банковской выгрузки в биллинг — PRD-lite

## Проблема

Ежедневную выгрузку платежей от банка бухгалтер разносит по счетам клиентов вручную. Дважды за квартал банк присылал один и тот же файл повторно; в первый раз повторное списание обнаружили только по жалобе клиента. Цена ошибки — деньги клиента, поэтому главная боль не «медленно», а **повторная выгрузка не должна приводить к повторному списанию**. Вторая боль — банк присылает корректировки сумм, и бухгалтерия должна уметь объяснить аудитору, что и почему изменилось.

## Пользователь

Бухгалтер. Увидел файл на S3 → запускает импорт руками из CLI → ожидает, что файл либо разнесён целиком, либо не разнесён вообще, и что состояние счетов можно объяснить аудитору.

## Success (done)

1. **Идемпотентность файла.** Повторный запуск импорта на уже обработанном файле не создаёт ни одной новой проводки: баланс всех затронутых счетов после второго прогона равен балансу после первого; CLI сообщает, что файл уже импортирован.
2. **Коррекция вместо дубля.** Для записи с уже известным идентификатором платежа и изменённой суммой прежняя проводка аннулируется, вместо неё создаётся новая; итоговый эффект на счёт равен новой сумме (не сумме двух).
3. **Аудит-след коррекции.** По каждой аннуляции доступна запись: кто/что аннулировало, когда, идентификатор платежа, сумма «было» и сумма «стало». Записи читаемы без доступа к БД-внутренностям (CLI-отчёт или экспорт), достаточны для ответа аудитору.
4. **Атомарность.** Если импорт прерывается на строке N (битая строка, падение процесса), после завершения в биллинге нет ни одной проводки из этого файла; повторный запуск после устранения причины разносит файл целиком. Частичного результата не существует ни в каком наблюдаемом состоянии.
5. **PII не в логах.** Ни при одном сценарии (успех, ошибка парсинга, необработанное исключение с трейсбеком, verbose-режим) телефон клиента не появляется в выводе CLI и в лог-файлах. Проверяется поиском тестового номера по всему логу.

## Ограничения

- Формат входа: CSV, один файл в сутки, источник — S3.
- Запуск: ручной, из CLI бухгалтером.
- Место в коде: `app/services/bank_import.py`, рядом с остальными интеграциями. Чтение — pandas (файл небольшой); это предпочтение, а не требование.
- Существующий API биллинга не изменяется — импорт встраивается поверх него.
- Дедупликация и аудит должны быть устойчивы к падению процесса, т.е. опираться на состояние в БД, а не в памяти. Обсуждалась таблица `imported_rows` с уникальным индексом по `(file_hash, row_no)` — как гипотеза реализации, не как требование.
- Цена ошибки — реальные деньги клиента: при сомнении корректнее не разнести, чем разнести дважды.

## NON-GOALS

- Автозапуск по событию из S3 — в первой версии только руками.
- Поддержка других банков и других форматов выгрузки — формат один.
- Любые изменения существующего API биллинга.
- Прогресс-бар в консоли — желателен («живой ли процесс»), но явно назван необязательным; не блокирует приёмку.
- Веб-интерфейс, планировщик, ретраи, алертинг.

## Открытое

1. **Строки без найденного счёта клиента.** Отбрасывать с отчётом или блокировать весь файл — не решено; оператор просил вариант **с обоснованием**, а не молчаливый выбор.
   *Рекомендация:* блокировать весь файл (fail-fast) — это согласуется с уже принятым требованием атомарности (критерий 4): «отбросить часть строк» — это ровно тот частичный импорт, который назван недопустимым, только незаметный. Ненайденный счёт означает либо рассинхрон справочников, либо чужой файл — оба случая требуют человека, а не тихого отчёта. Компромисс: сухой прогон (`--dry-run`), который печатает все проблемные строки разом, чтобы бухгалтер не чинил их по одной.
2. **Ключ дедупликации.** `(file_hash, row_no)` защищает от повторной присылки *того же файла*, но не от того же платежа, пришедшего в другом файле; коррекция при этом определяется по *идентификатору платежа*. Нужно решить, что является ключом идемпотентности — и что делать с одинаковым payment_id и **той же** суммой в новом файле (дубль или легитимный повтор).
3. Формат и место хранения аудит-следа (отдельная таблица, существующий журнал биллинга, экспорт).
4. Кто/что фигурирует в поле «кто аннулировал» при машинном импорте — учётка запустившего бухгалтера или системный субъект.
