# Импорт банковской выгрузки в биллинг — PRD-lite

## Проблема

Ежедневную выгрузку платежей от банка бухгалтер разносит по счетам вручную. Дважды за квартал банк присылал один и тот же файл повторно — и в первый раз двойное списание заметили только после жалобы клиента. Цена ошибки — деньги клиента и доверие к биллингу. Побочно: ручная разноска не оставляет внятного следа, объяснить аудитору «почему сумма изменилась» нечем.

## Пользователь

Бухгалтер. Видит, что файл за сутки пришёл, запускает импорт руками из CLI, ждёт результата, отвечает за итог перед аудитором. Не разработчик: диагностировать полусостояние системы не может и не должен.

## Success (done)

1. **Повторный импорт не двигает деньги.** Импорт файла → снимок остатков по затронутым счетам → повторный импорт того же файла → остатки идентичны, новых проводок нет. Запуск завершается успешно (не ошибкой) и сообщает, сколько строк новых, сколько уже разнесено.
2. **Коррекция заменяет, а не добавляет.** После импорта файла, где платёж с уже известным идентификатором приходит с изменённой суммой, на счёте действует ровно одна проводка по этому платежу — новая; сальдо соответствует новой сумме; прежняя проводка присутствует в системе как аннулированная.
3. **Аудит-след читаем без разработчика.** Для любой аннулированной проводки бухгалтер может получить: когда и в результате какого импорта/чьего запуска произошло аннулирование, сумма «была» и сумма «стала». Этого достаточно, чтобы воспроизвести историю платежа для аудитора.
4. **Нет частичного импорта.** При обрыве на середине файла (ошибка в строке, падение процесса) ни одна строка этого файла не разнесена: остатки и аудит-след совпадают с состоянием до запуска. После устранения причины повторный запуск разносит файл целиком.
5. **PII не утекает в логи.** После импорта файла с телефонами клиентов поиск по логам за период запуска не находит ни одного телефона — ни в обычных сообщениях, ни в сообщениях об ошибках и трейсбеках.

## Ограничения

- `[hard]` **Идемпотентность по содержимому выгрузки.** Сколько бы раз ни повторился импорт одной и той же выгрузки, финансовый эффект ровно один.
- `[hard]` **Атомарность на уровне файла.** «Разнесён целиком» и «не разнесён вовсе» — единственные допустимые состояния. Частичный результат хуже отсутствия импорта.
- `[hard]` **Совпадение идентификатора платежа при расхождении суммы = коррекция**, а не новый платёж: прежняя проводка аннулируется, новая занимает её место.
- `[hard]` **Аннулирование не стирает историю.** Прежняя сумма, новая сумма и обстоятельства изменения сохраняются и доступны для чтения бухгалтерией.
- `[hard]` **Телефон клиента (и любые PII из выгрузки) не попадают в логи ни на одном пути исполнения**, включая ошибочные. В проекте уже был инцидент с PII в логах.
- `[hard]` **Запуск ручной, инициируется бухгалтером.** Никаких фоновых или автоматических разносок.
- `[hard]` **Существующий API биллинга не меняется.**
- `[soft]` Понятный итоговый отчёт по запуску (что разнесено, что признано дублем, что скорректировано).
- `[soft]` Индикация прогресса в консоли — чтобы не гадать, жив ли процесс. Приятная мелочь, можно пожертвовать.
- `[soft]` Объём — один суточный файл; оптимизация под большие объёмы не требуется.

## NON-GOALS

- Автозапуск по событию из S3 или по расписанию — в первой версии только руками.
- Поддержка форматов других банков — формат один.
- Любые изменения существующего API биллинга.
- Автоматическое заведение отсутствующих счетов клиентов (см. «Открытое»).

## Открытое

1. **Строки с ненайденным счётом клиента.** Два кандидата: отбросить их с отчётом (файл разносится, часть строк не применена) либо заблокировать весь файл. Второй вариант согласован с инвариантом атомарности, первый — с продуктивностью бухгалтера. Решение за оператором: исполнитель обязан прийти с вариантами и обоснованием (влияние на атомарность, на восстановление, на действия бухгалтера после отчёта), молча не выбирает.
2. *(выявлено при синтезе, на сессии не обсуждалось)* **Коррекция платежа из уже закрытого учётного периода** — допустима автоматически, или требует отдельного ручного решения.
3. *(выявлено при синтезе)* **Что считать «тем же файлом»** — идентичность содержимого или идентичность имени/даты выгрузки. Спека фиксирует идемпотентность по содержимому; подтвердить, что банк не присылает содержательно разные выгрузки под одним именем.
