# Development workflow with Claude Code

Workflow для разработчика высокого класса на текущем поколении Claude Code и frontier-моделей.
Версионно-зависимый инвентарь built-ins намеренно не дублируется здесь — он живёт в одном месте: `.claude/docs/native-capabilities.md`.
Плотный портативный гайд от старта проекта до пайплайна — с акцентом на рычаги, двигающие качество. Первоисточники — внизу.

> Это human-facing гайд. Машинный routing-spine для main thread'а — `.claude/docs/workflow.md`.

---

## 0. Установка, на которой стоит всё остальное

- **Harness важнее модели — и его надо переучивать.** «Review your configuration every 3-6 months because instructions tuned for older models constrain newer ones» [[1]]. Под способной моделью **минимум обвязки = максимум продуктивности**: каждый компонент кодирует assumption «модель не умеет X»; умеет нативно → компонент вреден.
- **Не микроменеджь модель:** `effort=high` (дефолт 4.8 — не понижай на `medium` для нетривиалки), adaptive thinking ON (не управляй thinking-бюджетом вручную), sampling-параметры (`temperature`/`top_p`/`top_k`) на 4.8 убрать совсем (HTTP 400). [[2]]
- **Модель:** дефолт зависит от плана — топовая Opus на Max / Team Premium / Enterprise PAYG, **Sonnet-тир** на Pro / Team Standard; **Fable** — peer-модель поколения (`/model fable`, ~2× цена, thinking всегда ON, `/fast` неприменим, авто-fallback на Opus при safety-классификаторе). Blanket-switch не делать без доказанного лифта (lab A/B: ничья на bounded-задачах). [[2]]

## 1. Старт проекта — первая сессия

Цель первой сессии — **не код, а конфигурация окружения + контракт**, собранный из разговора (не upfront-анкетой — под 4.8 контракт всплывает органически).

- **`/init`** — Claude читает репо → стартовый `CLAUDE.md` (≤200 строк, **indexer, не store**: ссылается на `docs/`, не дублирует). Greenfield (нет кода / нет `.git`) → можно opinionated стек с rationale; existing → уважай конвенции **verbatim**.
- **Зафиксируй 5 пунктов контракта** по мере появления: стек (без молчаливых дефолтов) · project mode (new/mature) · acceptance criteria первого deliverable · механизм верификации (test cmd / lint / screenshot / manual) · sensitive paths → DENY.
- **Guardrails — сразу и реактивно.** Опасное (prod-config, реальная БД, deploy-скрипт, секрет) → `permissions.deny` в `.claude/settings.json` + строка «never touch X» в `CLAUDE.md`. **Механический guard переживает потерю контекста, инструкция — нет.** [[2]][[8]]

## 2. Требования и PRD

- **Думай вслух, не предполагай молча.** Несколько интерпретаций → выложи их, не выбирай тихо; проще решение → скажи. Уточняющие вопросы — только на развилках, реально меняющих *что* строить (не на том, что выводится из кода).
- **Контекст-слой = версионируемый артефакт, не одноразовый setup:** «Claude can't learn without you recording context… version it, grow it, maintain it». [[9]]
- **PRD-lite (1 страница), не бюрократия** (simplicity-first):

  ```
  Проблема:       что болит и у кого
  Пользователь:   кто, в каком сценарии
  Success (done): 3-5 наблюдаемых критериев (= acceptance criteria)
  Ограничения:    инварианты и контракты, помеченные [hard] / [soft]
  NON-GOALS:      что осознанно НЕ делаем (заморозка scope против drift)
  Открытое:       отложенные решения → ADR
  ```

  *NON-GOALS — не опускай эту строку: пусто = «не подумал», не «нет ограничений». Это гигиена scope, а не гейт, который что-то останавливает.*

- **Фиксируй *что* и *зачем*; *как* — не фиксируй.** Детектор: деталь влияет на бизнес-риск или архитектуру → пиши явно; чистая реализация (имена классов и функций, пути к файлам, схема таблиц, выбор библиотеки) → не пиши, это решение исполнителя. Разговор, из которого растёт спека, всегда содержит реализационные реплики — без детектора они оседают в *обязывающих* разделах и начинают подменять требование (A/B 2026-07-22, N=3×2: без правила 6/6 приманок в 3/3 прогонов, в одном реализационный ключ подменил acceptance-критерий; с правилом 0/6 без потери бизнес-фактов — `.claude/benchmark/spec-upstream-ab/`).
- **Ограничения — инварианты, не шаги.** «Операция идемпотентна», а не «сделай таблицу дедупа». `[hard]` — недоговороспособно; `[soft]` — можно пожертвовать ради простоты (это явное разрешение упрощать, а не украшение).

- **Acceptance criteria = наблюдаемое поведение через публичный интерфейс** («пользователь оформляет заказ с валидной корзиной»), не «сделать хорошо». Это **оракул, пронизывающий весь пайплайн**.
- **GLOSSARY first-use:** первый domain-термин/аббревиатура → запись. PRD живёт в `docs/`; состояние крупной задачи в полёте держит её открытая спека.

## 3. Дизайн и решения — до кода

Вход в фазу **Plan** (механика — в Спине ниже). Здесь фиксируешь *что решено и почему*.

- Архитектурные развилки — built-in **`Plan`-агент** / Plan mode с `xhigh` + `ultrathink`; облако — обычная сессия Claude Code on the web в plan mode, план забирается `claude --teleport <session id>`. [[3]]
- **Каждое нетривиальное решение → ADR** (Context / Decision / Consequences / Alternatives). Порог простой: *объяснение заняло бы >5 мин → ADR*.
- **Brownfield + трогаешь инварианты** → сначала read-only разведка built-in **`Explore`** (карта затронутых модулей · инварианты, которые нельзя сломать · blast-radius). Вывод **остаётся в контексте** — отдельный `docs/context/*.md` НЕ заводим (Explore перезапускаем по требованию под 1M-окном). Если fresh-context критику нужно прочитать карту через compaction — пришпиль её в context-секцию ADR или progress-журнал, не в новый формат.
- **Design-lite → (large only) грилл → ADR, в этом порядке.** Нетривиальное решение сначала живёт как *мутабельный* набросок (модель данных · ≥2 РЕАЛЬНЫЕ альтернативы · acceptance). На **medium** это абзац в плане — без spawn'а. На **large ∧ необратимо ∧ трогает инвариант** — прогони по нему тот же fresh-context рефутер, что в REVIEW/§8, с фальсифицируемым мандатом: «убей ≥1 альтернативу конкретным failure-сценарием или цифрой стоимости» (у прозы нет исполняемого оракула — грилл дизайна ловит меньше, чем грилл кода; это опция для дорогого-необратимого, не станция funnel'а). Победившее решение застывает в ADR; альтернативы не дублируй в обоих.
- Нетривиальный кодбейз → bootstrap проектных доков (`ARCHITECTURE` / `CODE-MAP` / `GLOSSARY` / `CONVENTIONS` / `ADR/` / `RUNBOOKS/`), **read-before-write** — реальное содержимое, не boilerplate.
- **Built-ins first:** не плоди кастомных `PM→Architect→Dev→QA` субагентов — оркестратор это **ты** (main thread). [[4]]

## Пайплайн одним взглядом

```
КОНТРАКТ      →  SPEC               →  BUILD (та же сессия)  →  REVIEW             →  СЛЕД
/init            интервью → SPEC.md    по SPEC.md, тесты        /code-review;        коммит
стек/mode        интерфейс дословно,   пишет исполнитель,       по уровню риска —    ADR
DENY-правила     ограничения scope,    «готово» = команда       ревью свежим         doc-with-code
                 GLOSSARY, ADR         + вывод                  контекстом против    MEMORY
                                                                SPEC.md, ≤3 раундов
   эскалация CHECK: работа не помещается в сессию → приёмочные тесты из SPEC.md отдельным контекстом до свежей сборки
      └──────────────── оракул (acceptance criteria) пронизывает весь поток ────────────────┘
```

Правило выбора режима: план в 2-3 шага в голове → single thread in-conversation · план становится кодом / сотни независимых операций / scope>1 контекст → dynamic workflow (`ultracode`) · дорого-необратимо и «выглядит готовым» → добавь fresh-context критика; глубину upstream (Discovery / PRD+NON-GOALS / design-lite→грилл→ADR) — по масштаб-строке Спины.

## Спина: Spec → Build → Review (ядро execution)

Масштабируй воронку под изменение, дефолт — **вниз**: trivial (1 строка) → сразу Build→Review · small (1 файл, ясный spec) → только acceptance-оракул · medium (multi-file / реальная развилка) → + design-lite абзац · large (cross-cutting / миграция / трогает **общий инвариант** / **незнакомая** brownfield-подсистема) → полный набор гейтов (Discovery-разведка · PRD+NON-GOALS · design-lite+грилл · ADR). Полный набор — нижняя строка и **исключение**, не ритуал; при сомнении классифицируй на класс ниже.

### SPEC — человек выравнивается на короткой спеке, а не на длинном плане
- *«Interview me until you could write the spec, then write it to SPEC.md»* [[2]] — модель расспрашивает, пока не сможет написать спеку; факты о коде ищет сама, а не спрашивает у человека.
- **Acceptance criteria явно** (что = «done») как проверяемые утверждения, non-goals, альтернативы. Это оракул, против которого крутится Review. Решение, объяснять которое >5 мин → ADR.
- **Интерфейс, зафиксированный запросом** (пути модулей, сигнатуры, классы ошибок), и ограничения scope — в `SPEC.md` дословно: сессия, которая собирает по файлу, другого не видит, а компакция теряет процессные ограничения чаще требований.
- Plan mode и built-in `Plan`-агент остаются для read-only разведки и архитектурных развилок, но поток их не требует.
- **Почему интервью, а не сразу код:** без него теряются правила, которых нет в запросе. В замере лабы (`.claude/benchmark/pipeline-ab/`) поток «интервью → спека → сборка в той же сессии» дал 100% скрытой приёмки в 8 прогонах из 9 за $1.0–1.4, ваниль без интервью — в 3 из 9, четырёхстадийный поток с отдельными тестами и ревью — 9 из 9 за $3.0–5.4, полный пайплайн Pocock — ещё в 3–4 раза дороже без прироста.

### Долгий проект — знания между сессиями
Контекст проекта живёт в файлах репо: в проектном `CLAUDE.md` — правило вести термины в `GLOSSARY.md`, решения (включая названные «на будущее») — в `docs/adr/` в той же сессии, и читать их перед работой. В многосессионном замере это держало ранние решения в 3/3 прогонах за +17% цены, а полный поток Pocock на каждую фичу — 2/3 в 11 раз дороже. Инструменты Pocock — по триггеру: фича больше сессии → `/to-spec` → `/to-tickets` и `/implement` по тикету (критерии тикета — исполнимые); туман → `/wayfinder`; после вехи → `/retro`. Подробно — `.claude/docs/workflow.md` § Долгий проект.

### CHECK — эскалация: когда сборка пойдёт в свежей сессии
- Триггер: работа не помещается в одну сессию, или ошибка дорога и не видна (парсеры, guards, инвариантные рефакторы). Свежая сессия, собирающая только по файлу, теряла требования (7 из 9); с приёмочными тестами из спеки — нет (9 из 9).
- Критерии из `SPEC.md` превращаются в приёмочные тесты **отдельным контекстом** (новая сессия или субагент) до реализации, через публичный интерфейс; ожидаемые значения — из спеки, а не из кода.
- Для исполнителя они read-only — **deny-правилом** на их путь, а не просьбой: *«If something has to happen every time, make it a hook, a deny rule, or a managed setting»* [[2]].
- Строгость — по классу модели исполнителя: слабее топовой — проверки непрерывно по ходу работы; топовой непрерывные проверки качества не добавляют и стоят дорого, но независимая проверка нужна в любом случае (достаточность одного финального гейта не измерена).

### BUILD — та же сессия, что писала спеку
- **1 main thread, 1M контекст, та же сессия, что писала `SPEC.md`**, если работа в неё помещается — фича целиком без handoff'ов; свежая сессия — только после CHECK. Single-agent — дефолт для most coding; multi-agent Anthropic явно называет «ill-suited» для большинства кодинга. [[4]]
- **Проверка pass/fail вместо TDD-ритуала**: порядок написания тестов и кода не предписывается — test-first как инструкция агенту не дал разницы в качестве при ×3–8.5 токенов, а red-шаг агенты пропускают или подделывают. Тест обязан быть способен упасть — доказывается поломкой кода, а не очерёдностью. «Готово» = тесты зелёные и критерии спеки покрыты, в отчёте команда и вывод. **Никогда не ослабляй тест ради зелёного.**
- **5 тест-инвариантов** (компактно): проверка в **той же сессии**, что и код · pass/fail, способна упасть, с доказательством · живёт **рядом с кодом** · **один тест — одно поведение** · **баг воспроизводится до фикса** (падающая проверка → фикс). Мокай только реально внешнюю границу (tool/API/network), не внутренности.
- **Surgical changes:** трогай только то, что требует задача — каждая изменённая строка трассируется к запросу. Не «улучшай» соседний код / форматирование, матчи существующий стиль; убирай только орфаны, созданные твоей же правкой (pre-existing dead code — упомяни, не трогай).
- Письменный чеклист шагов текущему поколению не выдаётся (task-list тулы off by default) — план держится в голове модели, а всё, что должно пережить сессию, пишется на диск.
- **Subagent — только** при (а) изоляции шумного вывода (broad scan, логи), (б) параллельности независимых задач, (в) независимом ревью свежим контекстом. Защита контекстного окна сама по себе — не основание. Иначе main thread сам. [[4]]

### REVIEW — главный рычаг
- Self-review + tests/lint/type-check всегда. **«Looks done ≠ is done»** — гоняй фичу end-to-end, не только unit/`curl`.
- **По уровню риска — одно ревью всей ветки свежим контекстом против `SPEC.md`**, только корректность, каждая находка с file:line (на работе в одну сессию оно находило замечания в 3 прогонах из 18 при 100% скрытой приёмки — поэтому по риску, а не всегда): *«report gaps that affect correctness and skip style»* — ревьюер, которого просят найти проблемы, найдёт что-нибудь всегда [[2]]. **Не больше 3 раундов** ревью → фикс, дальше — пересмотр подхода.
- **Человек — по уровню риска изменения**, а не автора: low — достаточно зелёных автоматических проверок, medium — один человек, high и sensitive-пути — двое; апрув агента за человеческий не засчитывается [[11]]. Качество тестов меряй сенсорами (mutation testing, статанализ), а не требованием test-first.
- **`/code-review`** — дефолтная ступень на каждый substantive change: built-in skill по рабочему диффу, локально и бесплатно, codebase-aware (`--fix` применяет находки, `--comment` кладёт inline-комментарии в PR). `/review` — алиас `/code-review`. Калибровка локального ревью — уровень effort (`low`/`medium` — только уверенные находки, `high`–`max` — шире охват); `REVIEW.md` настраивает **управляемый GitHub-сервис** Code Review и локальным ревью не читается. [[10]]
- **`/code-review ultra`** (алиас `/ultrareview`, CLI `claude ultrareview`) — cloud-fleet для high-stakes (security-путь, миграция, платежи): типично **5–10 мин, ~$5–20 за прогон через usage credits** (3 бесплатных на Pro/Max). Не на каждый PR — на каждый есть `/code-review`. [[10]]
- **Независимая верификация = fresh context, не self-recheck.** In-context «перепроверь себя» добавляет ≈0 — автор якорится на своём решении (Anthropic называет это **self-preferential bias** — одна из трёх failure-mode длинных/параллельных прогонов, наряду с *agentic laziness* «бросил, объявив done» и *goal drift* «констрейнты ушли через compaction»; изолированные субагенты лечат все три структурно [[7]]). Рычаг — **отдельный fresh-context критик (subagent / новая сессия), которому велено опровергать, а не подтверждать** (judge≠author / Planner→Generator→Evaluator). Сильный вариант: evaluator взаимодействует с **живым приложением** (Playwright MCP) перед оценкой, калиброван быть скептичным. [[3]] Находки ревьюера другой модели воспроизводятся до фикса: более слабый ревьюер, чьи находки применяются как есть, ухудшает сильного автора.

## Лестница верификации (cheapest → strongest)

`in-prompt check` → `/goal <condition>` (re-checked каждый ход [[5]]) → **Stop-hook** (детерминированный гейт) → **`/code-review`** (built-in, локально) → **fresh-context критик / dynamic workflow**.

Дай Claude петлю, которую он закрывает сам — «the single highest-leverage thing you can do» [[2]]. Анти-паттерн: одна end-session проверка (two-gate снижает false-completion ~35%→4%).

## Continuity — носитель один, и он уже есть

**Открытая спека и есть слой непрерывности**: она говорит, что должно стать правдой и
чего ещё нет; закрытая — история в git. Остановленная работа отчитывается как
**«блокировано на X, и вот кто разблокирует»** — это другое состояние, чем «ещё не
сделано».

Рамка: **файл = authoritative state, контекст эфемерен** — читаешь курированные
снапшоты, не историю. [[6]]

Параллельный журнал не заводится. Где проект уже ведёт свой — описательные коммиты,
трекер, ADR, workspace-конвенция — встречай его там; носитель, который проект ещё
не ведёт, не появляется «на будущее». Эмпирика (devlog #115, re-audit 2026-07-15):
прескриптивные форматы приживались в меньшинстве проектов, а где непрерывность
реально ценили — её переизобретали дешевле. Здесь же измерено предельно наглядно:
каталог in-flight-журнала, заведённый «на будущее», простоял четыре месяца и не
принял ни одного файла.

Где живёт состояние между сессиями — решает operator-global §6; проектным правилом
это не дублируется.

## Когда выходить за один контекст (и только тогда)

Scope **превышает один контекст** (codebase-sweep, миграция, trust-critical find→refute→converge):

- **Built-in dynamic workflows** — keyword **`ultracode`** (trigger word, не отдельный режим; голое «workflow» не триггерит) или просто попроси. Claude пишет собственный `.js`-harness под задачу: скрипт держит план/цикл/промежуточные результаты, в контекст входит только финал; **harness = output задачи, не предусловие**, переживает прерывание (resume). Стоит **заметно больше токенов** — не дефолт. [[7]]
- **НЕ** строй кастомный PM→Architect→Dev→QA pipeline (built-ins-first).
- **Недоверенный вход в fan-out → quarantine**: субагенты, читающие untrusted-контент (web/issues/email), отделены от тех, кто выполняет high-privilege действия — privilege-separation против prompt-injection. [[7]]
- Параллельные ветки — `-w` worktree + `claude agents` (`--json` отдаёт `sessionId`/`status`/`pid`/`cwd`, `--all` добавляет завершённые). Async-ожидание — `Monitor` tool, а где он недоступен (Bedrock/Vertex/Foundry, `DISABLE_TELEMETRY`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`) — background Bash с output-file и уведомлением по завершении. Bash `sleep`-цикл не годится ни там, ни там.
- **Backlog для large/кампаний — ОДИН редактируемый носитель, генерируемый one-way из spec** (переиспользуй `features.json` или Plan-файл — не заводи новый store и не строй md↔json зеркала с sync-машинерией). Не мандат единого формата: A/B (`campaign-backlog-ab`, drift=0, N=3) показал dual-canon безопасен — рычаг в one-way-генерации без mirror-sync, не в структуре.

## Ритуал поверх всего

Раз в 3-6 мес (или на мажорном апгрейде модели, или на дельте `claude --version` против зафиксированной baseline) — **аудит harness'а на staleness**: что модель теперь делает нативно → выкинуть. Сверяй **дельту от refresh-ledger** (последняя точка заземления: CC-версия / модель / проверенные источники), не «всё с нуля»; два прохода — external-intake (что сдвинулось снаружи: changelog, first-party docs, essays) и re-test (что из обвязки устарело). Быстрый тест «модель или обвязка» — `--safe-mode` (старт с отключёнными CLAUDE.md/skills/hooks/MCP): если без harness'а не хуже — компонент устарел. Под текущим поколением Anthropic сама убрала ручные context-resets и sprint-decomposition («context anxiety» ушла). [[1]][[3]]
